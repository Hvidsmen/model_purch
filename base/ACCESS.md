# Пользователи, группы и личные отчёты

После обновления выполните `python manage.py migrate --settings=portal.settings_local` на рабочей базе и перезапустите портал.

## Добавить пользователя

Администратор открывает «Пользователи и права» → Add user / «Добавить пользователя».

- Локальная запись: логин без домена и локальный пароль.
- Доменная запись: `DAICHI\samaccountname`, например `DAICHI\etladmin`. Пароль не заполняется, в AD ничего не создаётся и не меняется. Логин проверяет Windows при входе. Запись портала не имеет локального пароля.
- Логины доменных записей нормализуются в нижний регистр; дубликаты с другим регистром запрещены. Для заранее создаваемой записи нужен фактический samaccountname, а не UPN-псевдоним.
- Укажите роль. После создания открывается карточка пользователя: можно добавить ФИО/почту, изменить роль, назначить дополнительные группы или отключить признак Active.

## Политик

Эта роль открывает только:

1. «Мотивация. Дашборд»;
2. «Мотивация. Детально»;
3. «Факт закрытых сделок».

В карточке обязательны «Подразделение для личных отчётов» и «Точное ФИО автора сделки». После выбора подразделения форма загружает подсказки ФИО из DataWH по типу коэффициента «Политики». Если DWH временно недоступен, администратор может вручную скопировать точное ФИО из отчёта. Автоматического сопоставления только по фамилии нет.

Без настроенных групп тип коэффициента закреплён как «Политики», а подразделение берётся из карточки пользователя. При назначении групп подразделения и виды работника берутся из групп, как описано ниже. Автор сделки всегда закреплён персонально. Сервер применяет эти ограничения независимо от параметров URL, включая выборки для дополнительных столбцов, справочники фильтров, показатели выполнения, Excel и CSV. Доступ к планам, коэффициентам, общему отчёту по подразделениям, закупкам и администрированию запрещён. У пользователя без привязки доступа к отчётам нет. Смена привязки администратором применяется со следующего запроса.

Общие роли «Администратор», «Генеральный директор» и «Логист» сохраняют прежние права. Новая роль не создаётся из названия группы, похожего на роль; действуют только системные имена. Несколько разных системных ролей у одной записи приводят к отказу в доступе, а не объединению прав.

## Группы пользователей

В меню администратора «Группы пользователей» открывает отдельный экран с карточками. В каждой группе задаются:

- название;
- один вид работника (из справочника типов коэффициентов);
- одно или несколько подразделений;
- пользователи-участники.

У подразделений и пользователей есть поиск, галочки, «Выбрать все» и «Снять все». Пустой список подразделений не означает «Все»: сохранение такой группы запрещено. Пустой список участников допустим, чтобы подготовить группу заранее.

Для «Политика» настроенные группы задают доступ ко **всем подразделениям группы** и её виду работника. Несколько групп объединяют доступ, сохраняя связку «вид работника → подразделения»: если одна группа разрешает Политики/Москва, а другая Директора/Волга, нельзя получить Политики/Волга подменой фильтра. В отчёте можно выбирать только разрешённый вид работника и соответствующие ему подразделения. Автор сделки остаётся точным ФИО из карточки пользователя во всех случаях.

На дашборде и в факте сделок подразделение выбирается по одному; в детальном отчёте можно выбрать несколько разрешённых подразделений. При пустом выборе применяются разрешённые значения, а не общий доступ. Без настроенных групп продолжает действовать прежняя личная привязка. При наличии группы без подразделений, созданной в обход формы, доступ не расширяется: некорректная конфигурация не даёт права на все данные.

Группа сама не назначает системную роль. Для личного доступа сотруднику по-прежнему нужны роль «Политик» и точное ФИО в карточке. Администратор и существующая роль генерального директора сохраняют прежние более широкие полномочия. Группы без настройки доступа остаются обычными дополнительными группами Django. Системные группы ролей защищены от изменения через этот экран.

Редактирование группы применяется со следующего запроса. Участников можно назначать также в карточке пользователя. Группы портала не создают групп или пользователей в Active Directory и не меняют права Windows.

## Проверить права

Используйте «Просмотреть как пользователь». Меню и ограничения будут соответствовать выбранному пользователю; запросы на изменение данных в этом режиме запрещены. Кнопка в баннере возвращает администратора к его правам.


### Страница пользователей

`/accounts/users/` — управление учётными записями в оформлении портала: поиск,
создание локального пользователя, редактирование роли, групп, активности и личного
автора сделки. При редактировании пустой пароль сохраняет локальный пароль.
Доменным учётным записям назначается непригодный локальный пароль.
Кнопка в карточке запускает существующий режим просмотра без изменения данных.
Администратор не может отключить себя или снять собственную роль.

Поиск `/accounts/directory/?q=...` доступен только администратору. На Windows
использует NetGetDCName и NetUserEnum (NetAPI/RPC), без LDAP/LDAPS и без пароля
сотрудника, под учётной записью службы портала. Необходим доступ этой учётной
записи к домену и `PORTAL_AD_NETBIOS_DOMAIN=DAICHI`. Поиск от трёх символов
по логину или полному имени, до 50 результатов; отключённые записи исключены.
Выбор результата только заполняет карточку, сохранение выполняется отдельной
кнопкой. Роли не импортируются из AD. На Linux показывается сообщение о
необходимости Windows. Проверка реального DC выполняется на сервере заказчика.
Доменный вход по HTTP разрешается отдельно через `PORTAL_AD_ALLOW_HTTP=true`;
по умолчанию требуется HTTPS. Поиск работает независимо от способа входа.
Каталог загружается в фоне до двух минут; HTTP-запрос сразу возвращает
статус 202, браузер опрашивает готовность и показывает время ожидания.
Загрузка общая для запросов по разным фамилиям, готовый каталог кэшируется
на пять минут. Ошибка загрузки не подменяется пустым списком сотрудников.
