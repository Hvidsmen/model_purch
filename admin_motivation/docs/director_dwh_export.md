# Выгрузка директоров подразделений в DWH

Выгрузка утверждённых версий включает SubdivisionDirectorCoeff вместе с политиками и продажами в DataWH.motivation.SubdivisionMotiveCoeff. Глобальные директорские настройки сначала копируются в подразделения: в целевой таблице требуется конкретный филиал.

Для каждого сочетания «версия, филиал, товар, сотрудник» записываются пять строк:

- TypeCoeff — «Директора»;
- Segment — K0–K4, как у обычных коэффициентов;
- Coeff_ — соответствующее индивидуальное значение без суммирования сотрудников;
- EmployeeCode — уникальный код сотрудника из портала, NVARCHAR(64);
- EmployeeName — ФИО из справочника портала, NVARCHAR(255).

Поля EmployeeCode и EmployeeName добавляются как nullable, если отсутствуют. Операция выполняется до удаления старых строк, в той же транзакции экспорта. Нужны права ALTER на таблицу при первом запуске. Для политик и продаж оба поля передаются как NULL. Одинаковые ФИО не объединяются; связь определяется кодом. Имена берутся из текущего справочника, исторические имена модель портала не хранит.

В директорской форме нет отдельного VariationCalculate. При экспорте используется стандартный fallback SQL-расчёта: «Группа планов продаж» для 1. RAC / 2. VRF / 3. PROF, «Подразделение» для остальных групп. Отдельного нового правила выполнения плана в интерфейс не добавлялось.

Дата каждой записи равна effective_from её утверждённой версии. Черновики не выгружаются. Товары, встречающиеся только у директоров, также включаются в GoodsMotivation. При ошибке схема/замена данных откатываются и соединение закрывается.

## Зависимые SQL-объекты

Схема и фактическое определение vSubdivisionMotiveCoeffTo в этой среде не доступны. До индивидуального расчёта на DWH необходимо проверить:

1. Уникальные ключи целевой таблицы должны позволять несколько сотрудников на одну дату/филиал/товар/тип/сегмент. Старый уникальный ключ без сотрудника может заблокировать вторую строку; экспорт тогда откатится, существующие ограничения автоматически не удаляются.
2. View должна передавать EmployeeCode/EmployeeName и учитывать EmployeeCode при группировке/построении интервалов/PIVOT. Иначе MAX/SUM/LEAD может смешать сотрудников или их сроки действия.
3. Отдельная процедура расчёта факта должна сохранить код сотрудника в деталях и использовать ФИО директора как автора. Текущий SQL-кандидат из каталога review пока использует общее имя типа «Директора» и не адаптирован к индивидуальным полям view.

Это исправление обеспечивает отдельные записи сотрудников в исходной таблице экспорта. Изменение внешней view и расчётной процедуры требует их актуального определения; выгрузка таблицы сама по себе не подтверждает индивидуальный расчёт downstream.
