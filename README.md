# Портал планирования

Python 3.10–3.12, Django 5.2. Приложения: `PlanningSystem` (планы продаж и сезонность),
`model_purch` (сценарии закупок и расчёты), `admin_motivation` (коэффициенты мотивации),
`RefEditor` (справочники). Интерфейс использует Bootstrap/CoreUI и Plotly.

## Запуск на Windows (PowerShell)

Python 3.10 поддерживается. При первом запуске установите окружение:

```powershell
py -3.10 -m venv .venv310
.\.venv310\Scripts\python.exe -m pip install -r requirements.txt
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start.ps1
```

Если окружение `.venv` уже существует, `start.ps1` использует его, когда нет
`.venv310`. Активация окружения и права администратора не требуются. Параметр
`-ExecutionPolicy Bypass` действует только для запускаемого процесса PowerShell.

Скрипт показывает этапы подготовки и их длительность, выполняет проверки Django,
миграции и обновление статики. Перед изменением существующей базы создаётся
резервная копия с проверкой целостности. Если подготовка не удалась, сервер не запускается.
Полный просмотр SQLite при каждом обычном старте больше не выполняется: на большой
базе с историей расчётов он мог занимать продолжительное время ещё до первого сообщения.
Для отдельной полной проверки добавьте `-CheckDatabase`:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start.ps1 -Database .\db.sqlite3 -CheckDatabase
```

Сборка статики выполняется в том же процессе, что и подготовка базы. Сервер запускается
с `--skip-checks` после уже выполненных проверок, без повторения той же проверки Django.
Для прямого запуска без `start.ps1` предварительно выполните подготовку самостоятельно.
Он запускает сервер на `127.0.0.1:8000` без дополнительного процесса autoreload.
Для другого порта добавьте `-Port 8001`.
Чтобы слушать все сетевые интерфейсы на порту 8000:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start.ps1 -Database .\db.sqlite3 -BindAddress 0.0.0.0 -Port 8000
```

В браузере другой машины используйте `http://<IP сервера>:8000`, а на самом
сервере — `http://127.0.0.1:8000`. Для доступа по IP или имени сервера добавьте
его в переменную `DJANGO_ALLOWED_HOSTS` перед запуском, например:
`$env:DJANGO_ALLOWED_HOSTS = "localhost,127.0.0.1,192.168.221.178"`
(замените последний адрес фактическим IP сервера).

По умолчанию и обычные настройки, и `portal.settings_local` используют
`db.sqlite3` в корне проекта. Явно выбрать существующую базу можно так:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start.ps1 -Database .\db.sqlite3
```

Выбор сохраняется в `.local/config.json` и действует после закрытия PowerShell.
`DJANGO_DB_PATH`, если задана, имеет приоритет над сохранённой настройкой;
параметр `-Database` переопределяет выбор при запуске скрипта. Строки подключения
к MS SQL в этот файл не сохраняются: перед запуском задайте `MS_SQL_CONN_STR`.
Путь активной базы и выбранный сценарий видны на страницах модели закупок.
Если нужные данные были в `.local/db.sqlite3`, передайте именно этот файл через
`-Database`; скрипт не переносит и не объединяет базы автоматически.

### Обновление, которое убирает рабочую базу из Git

Рабочая SQLite-база и `.idea/` больше не отслеживаются Git. Перед **первым**
обновлением на эту версию остановите сервер и сохраните резервную копию вне
репозитория. Для вашей базы `db.sqlite3` и окружения `.venv310`:

```powershell
$dbBackup = Join-Path $env:USERPROFILE ("model-purch-before-update-" + (Get-Date -Format 'yyyyMMdd-HHmmss') + '.sqlite3')
.\.venv310\Scripts\python.exe -c "import sqlite3,sys; source=sqlite3.connect('file:db.sqlite3?mode=ro',uri=True); target=sqlite3.connect(sys.argv[1]); source.backup(target); target.close(); source.close()" $dbBackup
if ($LASTEXITCODE -ne 0) { throw 'Резервная копия не создана. Обновление остановлено.' }
git stash push -m "Database before untracking" -- db.sqlite3
git pull --ff-only origin main
if ($LASTEXITCODE -ne 0) { throw 'Git pull не завершён. База сохранена в резервной копии.' }
Copy-Item -LiteralPath $dbBackup -Destination .\db.sqlite3 -Force
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start.ps1 -Database .\db.sqlite3
```

Не выполняйте `git stash pop` для этой базы: после обновления она уже не
отслеживается Git. Созданный stash оставлен как дополнительная страховка.
Если есть другие незакоммиченные изменения кода, сначала сохраните их отдельно.
После этого первого обновления обычный `git pull` больше не конфликтует с
изменениями рабочей базы. Новый клон создаёт пустую базу; существующую рабочую
базу нужно передать или восстановить из своей резервной копии.

### Резервные копии

`manage.py migrate` автоматически создаёт копию существующей SQLite-базы в
`.local/backups/` перед применением миграций. При ошибке копирования миграции
останавливаются. Режимы `migrate --plan` и `migrate --check` базу не копируют.
Используется SQLite Backup API, поэтому копируются и зафиксированные изменения
из WAL. Копии проверяются через `PRAGMA quick_check` и не удаляются автоматически.

Для резервного копирования в любой момент:

```powershell
.\.venv310\Scripts\python.exe manage.py backup_database --settings=portal.settings_local
```

Перед восстановлением остановите все процессы приложения, сохраните текущее
состояние отдельной копией и восстановите выбранную копию в отдельный файл.
Передайте этот файл через `start.ps1 -Database`: исходная база останется сохранена.
Резервные копии в `.local` не защищают от потери диска — копируйте их на отдельный носитель.

```bash
python3.10 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Настройка сохраняется в `.local/config.json`, как и на Windows. Загрузки сохраняются
в `.local/media`. Для пустой БД создайте администратора через `manage.py createsuperuser`

Основные страницы: `/`, `/model_purch/`, `/plannging_system/`, `/ref_editor/ref-store-group/`.
Написание `plannging_system` сохранено для совместимости существующих адресов.
Проверки выполняются с отдельной временной тестовой БД, без корпоративных записей.

## SQL Server и расчёты

Локальный режим позволяет разрабатывать интерфейс и выполнять тесты без SQL Server.
Синхронизация, расчёт заказов, графики корпоративных остатков и импорт данных в DWH
требуют реального доступа к серверу и схемам. Эти операции изменяют корпоративные
таблицы; тесты заменяют подключения к SQL Server и не выполняют их на реальном сервере.

Настройте переменные процесса (не сохраняйте пароли в Git):

- `MS_SQL_CONN_STR`: ODBC-подключение к базе `ModelPurch`.
- `DWH_SQL_CONN_STR`: ODBC-подключение к базе `DataWH`.
- `DJANGO_DB_PATH`: необязательный путь к SQLite.
- `DJANGO_SECRET_KEY`: ключ Django; обязателен при `DJANGO_DEBUG=false`.
- `DJANGO_ALLOWED_HOSTS`: разрешённые имена серверов через запятую.

На машине нужен ODBC-драйвер, указанный в строке подключения. Старое подключение
`SQL Server` с `Trusted_Connection=yes` зависит от Windows-аутентификации; для Linux
нужны подходящий драйвер и поддерживаемая сервером схема аутентификации.
SQL-процедуры, представления и SQL Agent job `ModelPurch` в этом репозитории отсутствуют.
Полный расчёт нельзя проверить только по Python-коду без этих внешних компонентов.
Последний шаг запускает задание пересчёта куба, но не подтверждает его завершение.

`portal.settings` сохраняет старое Windows-подключение как значение по умолчанию,
если переменные не заданы. Для разработки без корпоративной сети используйте
`portal.settings_local`. Старые Dash-модули отключены по умолчанию: действующая страница
графиков использует JSON API и Plotly. Их отдельная интеграция требует настройки
`django-plotly-dash`, его маршрутов и приложений; один флаг не заменяет эту настройку.

## Уникальность PGGoods

Ключ товара: **сценарий + planning_group**. Регистр, пробелы по краям и разные
Unicode-представления одной буквы не создают новую группу. `planning_sales` и
`group_goods` — параметры товара, а не дополнительные части ключа. Название для
отображения сохраняется; служебный `planning_group_key` обеспечивает одинаковую
идентичность в SQLite и MS SQL независимо от правил сравнения текста базы.

Миграция `model_purch.0010` устраняет существующие дубли: оставляет запись с **наибольшим
ID**, без смешивания её параметров со старыми. Полные снимки всех записей каждой
дублирующейся группы сохраняются в `PGGoodsDuplicateArchive`, доступном для просмотра
в админке Django. Снимки включают также оставленную версию. Перед миграциями сделайте
копию своей рабочей SQLite-базы и убедитесь, что `DJANGO_DB_PATH` указывает именно на неё.
В новой пустой `.local/db.sqlite3` миграции не исправляют исходную `db.sqlite3`.

Копирование товаров, импорт Excel и синхронизация SQL сопоставляют записи только по
сценарию и нормализованной плановой группе. Повторный импорт Excel без ID обновляет
существующую группу. Если строка Excel с ID пытается переименовать товар в группу,
которая уже занята другой записью, эта строка отклоняется; остальные строки продолжают
обрабатываться. Для административного импорта используйте:

```powershell
.\.venv310\Scripts\python.exe manage.py import_pggoods --scenario 1 --dry-run --settings=portal.settings_local
```

Замените `1` на нужный ID сценария. Без `--dry-run` импорт сохраняет записи, а `--clear`
очищает только выбранный сценарий, а не все сценарии.

На следующем экспорте сценария в MS SQL приложение также подготовит таблицу
`portal.PGGoods`: добавит ключ, архивирует существующие дубли **во всех сценариях**
в `portal.PGGoodsDuplicateArchive`, оставит наибольший SQL ID в каждой группе и создаст
уникальные индексы по сценарию и ключу группы, а также непосредственно по
`scenario_name + planning_group` с правилами сравнения SQL Server. Если собственная
collation SQL Server считает равными дополнительные названия (например, с разными
диакритическими знаками), экспорт отклоняется и откатывается вместо создания дублей.
Все изменения данных этого экспорта
выполняются в одной SQL Server транзакции; ошибка вызывает откат. Эта подготовка
требует прав на изменение таблицы и создание индекса. Перед первым экспортом сделайте
обычную резервную копию корпоративной базы. После обновления сначала выполните
миграции SQLite, затем экспортируйте сценарии, чтобы передать выбранные локальные
параметры в SQL Server. Служебный ключ не меняет названия групп в расчётах.

Live-миграция MS SQL не выполнялась в облаке: SQL Server здесь недоступен. Автоматические
тесты проверяют подготовку SQL, архивирование, ключ MERGE и откат через заменённое
подключение. Миграция SQLite проверена также на отдельной копии исходной базы.

## Ошибка «argument 1 must be a string or unicode object» на шаге подготовки

В `portal.settings_local` корпоративное подключение отключено, пока не задана
`MS_SQL_CONN_STR`. SQLite-база с данными интерфейса не заменяет SQL Server для
алгоритма. Все SQL-шаги алгоритма теперь используют общий валидатор подключения,
потребляют результаты всех процедур, откатывают ошибочный шаг и закрывают подключение.
Отсутствующее подключение выдаёт сообщение с названием нужной переменной.

На Windows в корпоративной сети, если используется прежний драйвер `SQL Server` и
Windows-аутентификация, задайте переменную **в том же PowerShell перед запуском Django**:

```powershell
$env:MS_SQL_CONN_STR = 'DRIVER={SQL Server};SERVER=vm-dwh;DATABASE=ModelPurch;Trusted_Connection=yes;'
.\.venv310\Scripts\python.exe manage.py runserver --settings=portal.settings_local
```

Это подключение использует текущую учётную запись Windows, без пароля в проекте.
Имя установленного драйвера можно проверить, не раскрывая строку подключения:

```powershell
.\.venv310\Scripts\python.exe -c "import pyodbc; print(pyodbc.drivers())"
```

Если драйвер или способ аутентификации отличаются, используйте соответствующую
строку подключения, предоставленную администраторами. После изменения переменной
перезапустите Django и создайте новый запуск алгоритма: ранее сохранённая ошибка
старого запуска автоматически не изменится. При повторной ошибке подключения
проверьте доступ текущей Windows-учётной записи к `vm-dwh` и базе `ModelPurch`.

## Новые поля Django и экспорт в MS SQL

Перед экспортом сценария проверяются колонки SQL-таблиц `portal.Scenario`,
`portal.ScenarioPlanSales`, `portal.Purch`, `portal.PurchPay`, `portal.PGGoods` и
`portal.KindLagPay`. Отсутствующие простые поля добавляются через `ALTER TABLE ADD`;
существующие колонки и их типы автоматически не изменяются и не удаляются.
Новые колонки создаются nullable, чтобы сохранить записи ранее экспортированных
сценариев. Их значения заполняются при следующем экспорте соответствующего сценария.

`Purch.lage_make` теперь передаётся в `portal.Purch.lage_make`. Для платежей
экспортируются `kind_lag_pay_id` и текстовое название `kind_lag_pay`, а справочник
`KindLagPay` обновляется в `portal.KindLagPay` с исходными Django ID.

Новые текстовые, числовые, логические поля, даты/время, UUID, пути файлов и JSON
выгружаются по метаданным моделей без ручного расширения основного SQL-запроса.
Datetime записывается в UTC без смещения в колонку DATETIME2; Decimal передаётся
строкой без потери точности. SQL-идентификаторы вставляемых платежей используются
для записи дополнительных полей, а локальные ID не подменяют IDENTITY SQL Server.

Новые ForeignKey требуют явного сопоставления: нужно выбрать ID SQL-справочника
или текстовое значение и настроить экспорт этой связи. Неизвестная связь или тип
поля вызывают ошибку вместо молчаливого пропуска. При добавлении нового простого
поля в Django также нужна обычная миграция вашей SQLite-базы. Изменение существующих
SQL-типов и пользовательских NOT NULL ограничений требует отдельной миграции SQL.

Для обновления существующих SQL-таблиц учётная запись экспорта должна иметь право
`ALTER TABLE`. Перезапустите Django после обновления кода и повторно экспортируйте
сценарий. Изменения данных откатываются при ошибке; успешно выполненные добавления
SQL-колонок могут сохраняться независимо от последующей ошибки экспорта.

### Фрахт по сценариям

Фрахт расположен **над таблицей товаров** и относится к выбранному сценарию.
Введите цену за контейнер (до двух знаков после запятой), затем нажмите «Сохранить».
Копирование из сценария переносит фрахт, таможенную ставку и стоимость доставки; объём контейнера задаётся отдельно
у каждого товара. Отдельного пункта меню «Фрахт» больше нет; прежний адрес
`/model_purch/freight/` перенаправляет к настройкам на странице товаров.

Прежний сценарный объём сохранён как архивное поле без редактирования, чтобы
сохранить данные и совместимость существующего SQL-экспорта. Актуальный объём
выгружается для каждого товара в `portal.PGGoods.container_volume`.

### Массовый экспорт сценариев в MS SQL

На странице **Сценарии** отметьте нужные строки галочками (галочка в заголовке
выбирает все) и нажмите **Экспортировать выбранные в MS SQL**. Выбранные сценарии
экспортируются последовательно вместе с планами продаж, закупками, платежами,
товарами и заполненными параметрами фрахта. Существующие записи обновляются.

Каждый сценарий экспортируется отдельно: ошибка откатывает его данные и не
останавливает остальные сценарии. Страница показывает результат по каждому
сценарию и общий итог. Не закрывайте страницу до завершения экспорта.


## Общий справочник закупок

Закупки и графики платежей больше не принадлежат сценарию. Вкладка **Закупки**
показывает единый справочник; его можно заполнять ещё до создания сценариев.
Удаление сценария сохраняет закупки. Название закупки уникально без учёта регистра,
краевых пробелов и эквивалентных Unicode-представлений.

Миграция `0013` объединяет существующие записи с одинаковыми названиями.
Действующей остаётся запись с **наибольшим ID** и её полный график платежей.
Все исходные записи, включая оставленные, сохраняются вместе с платежами и
прежним ID сценария в `PurchScenarioArchive` (доступен только для чтения в админке).
Перед миграцией обычный запуск `start.ps1` автоматически создаёт резервную копию SQLite.

На вкладке закупок показаны названия из колонки **Закупка** товаров всех сценариев,
для которых нет записи справочника. Ссылка **Создать закупку** подставляет название.
Пустая колонка также отмечается. Экспорт проверяет покрытие товаров выбранного
сценария **до подключения к MS SQL**; общий расчёт проверяет все сценарии.

В MS SQL общий справочник и платежи выгружаются **отдельно для каждого сценария**:
`portal.Purch.scenario_name` и связанные `portal.PurchPay` сохраняют прежнюю структуру.
Повторный экспорт обновляет настройки и удаляет отсутствующие в справочнике закупки
только из экспортируемого сценария. Экспорт других сценариев не затрагивается.
Изменение справочника или графика платежей делает экспорты всех сценариев устаревшими:
повторите массовый экспорт перед общим расчётом. Автоматическая синхронизация при
создании/редактировании сценария добавляет только отсутствующие закупки и сохраняет
введённые пользователем общие настройки.

## Надёжность сценариев и расчёта

Общий выбор сценария сохраняется в сессии браузера при переходах между товарами,
фрахтом и расчётом. Закупки — общий справочник без выбора сценария.
Формы создания и копирования сценарных данных передают целевой
сценарий явно, поэтому выбор в другой вкладке не перенаправляет сохранение.
Удалённый сценарий исключается из выбора; ошибочный явный ID не заменяется
последним сценарием.

Перед расчётом проверяются даты, уникальность названия сценария, наличие товаров,
конечные неотрицательные цены и коэффициенты, положительные объёмы, проценты
от 0 до 100, неотрицательные лаги и сумма платежей по каждой закупке (100%,
допуск 0,01 процентного пункта). Отрицательный лаг самого платежа допускается
для предоплаты. Фрахт необязателен; заполненные параметры проверяются.

Успешный экспорт записывает время, снимок всех параметров и SHA-256 в
`ScenarioExport`. Страница расчёта показывает готовность и последний экспорт
**каждого сценария**, а также последние пять общих запусков со снимками параметров.
Ранее выполненные экспорты не имеют снимков: после обновления повторите экспорт
всех сценариев перед первым расчётом.

Расчёт выполняется **по всем сценариям за один запуск**, как в исходном алгоритме.
Выбор в верхней панели используется для редактирования и не ограничивает расчёт.
Перед запуском проверяются все локальные сценарии, для каждого сохраняются параметры
и время экспорта. Устаревший экспорт любого сценария блокирует общий запуск.
Изменение параметров, добавление или удаление сценария во время расчёта блокирует
следующий шаг. Одновременно разрешён один общий запуск; остановленный между шагами
запуск можно завершить на странице расчёта.

Шаг расчёта вызывает `calc_purch()` без ограничения сценария: он читает все сценарии
из подготовленных данных MS SQL, очищает `dbo.PlanIncome` и сохраняет общий результат
для всех сценариев одной транзакцией. Общие SQL-процедуры подготовки и обновления
таблиц, а также OLAP job вызываются один раз. Их исходников в репозитории нет,
поэтому реальная интеграция требует проверки на корпоративном сервере.
Статус последнего шага означает отправку задания OLAP, а не завершение пересчёта.
Старые запуски, начатые в режиме одного сценария, сохраняют ранее зафиксированный
охват; новые запуски всегда общие.

Экспорт, копирование, выбор сценария, резервное копирование и проверки расчёта
находятся в `model_purch/services/`. HTTP-обработчики используют эти сервисы.
Bootstrap для форм и модальных окон хранится локально, чтобы копирование не зависело
от доступности CDN. Иконки также хранятся локально; Plotly использует прежний внешний ресурс.

## Версии общих коэффициентов мотивации

Страницы `/admin_motivationglobal_coeff` и коэффициентов подразделений содержат
один общий список версий, создание новой версии и историю периодов действия.
Выбор сохраняется при переходах между страницами. Миграция `admin_motivation.0006` сохраняет
существующие коэффициенты без изменения числовых значений в исходной версии
с датой **01.01.2001**. Для всех последующих версий обязательна дата начала действия,
обычно позже последней сохранённой даты. Для той же или более ранней даты отметьте
разрешение замены. Дата не может быть раньше 01.01.2001; создание черновика само по себе
не меняет утверждённую историю.

Новая версия копирует сохранённые глобальные коэффициенты, настройки всех подразделений
и коэффициенты руководителей последней версии. Перед созданием
сначала сохраните изменения таблицы. Новую версию можно создать и находясь в истории:
источником всё равно будет последняя версия. Редактировать, загружать Excel и удалять
строки можно только в последнем черновике; утверждённые и предыдущие версии остаются доступными для просмотра.
Удаление строки не удаляет товар и значения предыдущих версий. Даты созданных
версий не меняются. Админка предоставляет версии и коэффициенты только для чтения.

Утверждённая версия действует до дня перед началом следующей утверждённой версии. Последняя не имеет даты
окончания. Будущую версию можно подготовить заранее: копирование из глобальных коэффициентов
использует **ту же выбранную версию**. Значения других версий не меняются. Календарная дата и время создания в истории — по Москве.
Индивидуальные коэффициенты подразделений не изменяются автоматически при правке
глобальных: копирование остаётся отдельным действием в выбранной версии.
История всех настроек хранится в локальной базе Django.

Просмотр страницы и истории работает с сохранёнными справочниками и не требует
подключения к DWH. Кнопка **Обновить справочники из DWH** обновляет списки для добавления
товаров; для неё нужна `DWH_SQL_CONN_STR`. Сохранение коэффициентов выполняется одной
транзакцией: некорректное число откатывает все изменения формы.


Миграция `admin_motivation.0007` переносит существующие индивидуальные и
руководительские коэффициенты в исходную версию с **01.01.2001**, сохраняя ID и значения.
Если глобальные версии уже созданы, эти текущие настройки копируются в каждую из них:
старая база не содержит отдельной истории подразделений. В дальнейшем новая общая
версия копирует всю предыдущую конфигурацию. Исторические версии на обеих страницах
и в админке доступны только для чтения. Новая версия, созданная на странице подразделения,
возвращает пользователя в то же подразделение с выбранной новой версией.

Выгрузка в DataWH отправляет все действующие утверждённые версии с точными датами
начала действия из каждой версии, включая исходную дату 01.01.2001. Выбор года и квартала
не нужен. Черновики и заменённые версии не выгружаются. Данные в целевых таблицах начиная
с первой утверждённой версии заменяются атомарно; более ранние записи сохраняются.
Перед выгрузкой форма показывает список версий и дат.

## Сценарии планов продаж и расчёт мотивации

В панели мотивации добавлена вкладка **Планы продаж** (`/admin_motivationsales_plans`).
Создайте сценарий с названием и значением `DataWH.planning.PlanSales.Version_`.
Кнопка **Получить версии из MS SQL** заполняет подсказки; значение можно ввести вручную.
**Загрузить план из MS SQL** выполняет параметризованный запрос из
`admin_motivation/sql/sales_plan.sql`, используя `DWH_SQL_CONN_STR`.
Это чтение DataWH; расчёт и результаты сохраняются в локальной базе Django.
Миграция `admin_motivation.0008` создаёт отдельные таблицы сценариев и строк плана,
не меняя существующих коэффициентов или сценариев закупок.

Товар сопоставляется точно по тройке: группа планов продаж, группа ERP, марка.
Для `1. RAC`, `2. VRF`, `3. PROF` группа ERP сохраняется, иначе используется `*`.
Марка сохраняется для бытовых и полупромышленных кондиционеров, мульти-сплит
и VRF; иначе используется `*`. Звёздочка — конкретная агрегированная категория,
не поиск произвольной марки. Подразделение сопоставляется по `SubdivisionName`
из SQL и `subdivision_key` локального справочника.

Распределение O0–O4 берётся из факта за четыре предыдущих календарных года,
с исключениями каналов и подразделений из исходного SQL. Если подходящего факта
нет или его суммарная выручка равна нулю, весь план относится к O0.
Дата плана сохраняется. Глобальный план — сумма строк подразделений по дате
и товарной тройке, включая отдельные суммы O0–O4.

**Рассчитать мотивацию** выбирает общую версию коэффициентов, действующую на дату
каждой строки. При наличии утверждённых версий используются только они; до первого
утверждения существующий расчёт по черновикам остаётся предварительным. Глобальный план использует глобальные коэффициенты, подразделение —
свои индивидуальные. Соответствие сегментов: `K0 → O0`, …, `K4 → O4`.
Для политик и продаж независимо считается `Σ(Ki × USD_Oi)`, итог — сумма обеих
мотиваций. Коэффициенты хранятся долями: `0.1` означает `10%`; руководительские
коэффициенты и варианты других формул в этот расчёт не включаются.
При отсутствии точного коэффициента используется минимальный коэффициент по той же
группе планов продаж и типу («Политики» или «Продажи») среди всех товарных групп,
марок и сегментов K0–K4. Поиск ограничен версией на дату плана и тем же подразделением;
для глобального плана используются только глобальные коэффициенты. Точное значение,
включая ноль, имеет приоритет. Отрицательные значения участвуют в минимуме.
Если нет версии на дату плана или минимума в группе, используется минимум всей
соответствующей таблицы по типу (политики/продажи), включая все группы, версии и
для таблицы подразделений все подразделения. Глобальный и индивидуальный наборы
не смешиваются. Если в таблице вообще нет значений нужного типа или найдено
неоднозначное точное соответствие, расчёт завершается ошибкой с сохранением результатов.
Расшифровка отмечает подстановку минимума и сохраняет исходные группу, марку и
сегмент коэффициента; CSV содержит источник `exact`, `group_minimum` или `table_minimum`, а также
фактические версию, подразделение и группу планов источника. При отсутствии версии
на дату плана поле версии строки пустое, использованные версии сохранены для каждого сегмента.

Результат сохраняет использованную версию, значения коэффициентов, суммы сегментов
и вклады каждого сегмента. Редактирование коэффициентов не меняет сохранённый
результат: для обновления нужен повторный расчёт. Вкладки глобального плана и
подразделений имеют отдельные итоги; их нельзя складывать друг с другом.
Основной отчёт показывает итоги за весь период в сворачиваемом дереве и CSV
агрегированных строк выбранного разреза; расчётные расшифровки сохраняются в базе. Повторная загрузка заменяет только выбранный сценарий и сбрасывает его
расчёт; пустой план, ошибка SQL или некорректные данные сохраняют прежние результаты.

Загрузчик читает результат по именам столбцов из `cursor.description`, поэтому
положение `Date_` и порядок сегментов не влияют на импорт. `Date_` принимается как
дата/дата-время Python либо ISO-строка от SQL-драйвера (`YYYY-MM-DD`, в том числе
со временем). Текущий SQL возвращает столбцы в порядке: подразделение, группа
планов, группа ERP, марка, дата, сумма, USD_O0–USD_O4. Версия сценария передаётся
параметром в `DECLARE @params_scenario nvarchar(255) = ?`. Ошибки данных показывают
номер строки и конкретное поле; неполные данные не заменяют сохранённый план.

Пустая группа планов продаж (`NULL`, пустая строка или пробелы) относится к
`9. OTHER`, как в исходном SQL. Если после этой замены несколько строк имеют
одинаковые дату, подразделение и товарную классификацию, их суммы и суммы O0–O4
объединяются. Для мотивации нужны коэффициенты категории `9. OTHER` соответствующей
версии; сами коэффициенты не подставляются и не создаются автоматически.

### Скорость и прогресс операций планов продаж

Расчёт читает строки и сохраняет результаты пакетами по 1000, в одной общей
транзакции. Вместо большого ORM `bulk_update` с CASE-выражениями для всех JSON-строк
используется параметризованный `executemany`, с преобразованием значений полями
Django. Справочники коэффициентов читаются простыми кортежами, числовые значения
готовятся один раз; выбранные версии и найденные коэффициенты переиспользуются.
Кэш коэффициентов ограничен 10 000 значениями. Контрольный локальный прогон
5000 строк: до изменений 5,119 сек., после около 1,1 сек.; это измерение расчёта
в SQLite, время запроса корпоративного SQL в него не входит.

Импорт читает MS SQL через `fetchmany(2000)`; сырые строки не собираются через
`fetchall`. Запись плана также выполняется пакетами. Фильтр четырёх предыдущих
календарных лет выражен диапазоном `ClosedDealDate`, чтобы SQL Server мог
использовать существующий индекс даты; сам период и формулы не изменены.

Кнопки загрузки и расчёта показывают этап, время, число обработанных строк и
полосу прогресса. Во время выполнения запроса SQL и чтения данных, когда общее
число строк неизвестно, индикатор показывает ожидание вместо условного процента.
Прогресс передаётся в браузер потоковым HTTP-ответом; 100% показывается только
после успешного завершения транзакции. Ошибки видны в панели, прежние результаты
сохраняются. Без JavaScript остаётся обычная отправка формы.

Реализация предназначена для текущего локального `start.ps1` / одного процесса
Django и не требует Redis или Celery. Второй запуск операции того же сценария
в этом процессе блокируется до завершения первой. При закрытии страницы работа
продолжается в сервере; после возврата обновите страницу, чтобы увидеть результат.
Для нескольких независимых процессов сервера потребуется общая очередь задач
и межпроцессная блокировка. Сервер должен пропускать потоковый HTTP-ответ без
буферизации; ответ содержит `X-Accel-Buffering: no`.


### Итоги планов продаж за весь период

Основной отчёт не содержит строк по датам. Итоги вычисляются SQL-агрегацией
сохранённых результатов по подразделению, группе планов продаж, группе ERP и
марке/бренду. Сначала коэффициенты применяются к каждой дате, затем мотивация
суммируется: версии внутри периода учитываются правильно.

Дерево имеет четыре уровня: подразделение → группа планов продаж → группа ERP
→ марка/бренд. Каждый уровень показывает план, политики, продажи и общую
мотивацию. В глобальном разрезе корень «Глобальный план» открыт, остальные
группы закрыты; в разрезе подразделений все подразделения изначально закрыты.
Кнопки «Развернуть всё» и «Свернуть всё» управляют всем деревом.

Фильтры: подразделение (в подразделенческом разрезе), группа планов продаж,
группа ERP и марка/бренд. Фильтры применяются до агрегации: верхние итоги,
подытоги дерева и CSV всегда соответствуют выбранным значениям. «Сбросить»
возвращает весь выбранный разрез. Переход между разрезами сохраняет товарные
фильтры; фильтр подразделения при переходе к глобальному плану сбрасывается.
Если мотивация ещё не рассчитана, отчёт показывает план и прочерки в суммах
мотивации с предупреждением; ноль не подставляется вместо отсутствующего результата.

«Скачать CSV» выгружает итоговые строки марок за весь период, без дат и без
повторения подытогов (их нельзя складывать второй раз). Для технического аудита
снимков коэффициентов прежний датированный экспорт остаётся доступен через
`export=details` с теми же фильтрами. Сам отчёт не читает большие JSON-расшифровки:
группировка и суммы вычисляются в локальной базе данных.


### Утверждение и сравнение мотивации

На страницах глобальных коэффициентов и подразделений выберите один загруженный
план продаж и, при необходимости, базовую версию. Выбор плана и базы общий для обеих
страниц. Сравнение показывает политики, продажи и общую мотивацию за весь период:

- **Утверждённый** — все действующие утверждённые версии по датам плана.
- **Базовый** — одна выбранная сохранённая версия на весь период, независимо от её даты.
  Последний редактируемый черновик нельзя выбрать базой; заменённые версии доступны.
- **Текущий** — утверждённая история до даты выбранной версии, затем выбранный набор
  до конца плана. Изменения коэффициентов в ячейках и отмеченные удаления глобальных
  товаров учитываются сразу, без сохранения.

Для отсутствующих коэффициентов минимум ищется внутри каждого варианта отдельно,
по тем же правилам группы/таблицы и типа «Политики» или «Продажи». Черновик не меняет
минимум утверждённого варианта. Глобальные и подразделенческие таблицы не смешиваются.
На странице подразделения сравнение относится только к этому подразделению.
Числа отображаются без десятичных знаков, расчёт сохраняет исходную точность.
Переключатели скрывают вариант вместе с его разницей: по умолчанию утверждённый
показан, базовый скрыт. Видимость сохраняется в браузере для обеих страниц.

**Просмотреть и утвердить весь набор** открывает предварительный просмотр: влияние
на глобальную сумму и сумму всех подразделений, дату и список заменяемых версий.
Утверждаются одновременно глобальные, подразделенческие и руководительские настройки.
Несохранённые значения коэффициентов текущей страницы сохраняются при утверждении;
остальные настройки (например, руководители и варианты формул) сохраните заранее.
Можно утвердить без плана, но тогда оценка суммы не выполняется.

Если новая дата не позже действующих утверждённых версий, они исключаются из действующей цепочки
с этой даты включительно. Для этого в окне утверждения нужно подтвердить замену.
Если новая дата не позже выбранной базовой, также выводится предупреждение; базовая
остаётся неизменным эталоном. Старые значения, даты и связи с заменившей версией
сохраняются. Исторический черновик можно утвердить как сохранённый снимок, с таким же
предупреждением о замене.

После утверждения набор доступен только для просмотра: изменения делайте в новом
черновике. Если после предварительного просмотра другой пользователь изменил план
или коэффициенты, подтверждение отклоняется; повторите просмотр. Сохранённые результаты
планов не меняются автоматически — для их обновления снова запустите расчёт.

Миграция `admin_motivation.0009` сохраняет существующие коэффициенты и назначает
существующим версиям статус **Черновик**. Она не выполняет утверждение за пользователя.
После обновления сначала просмотрите и утвердите исходную версию, затем последующие
по порядку дат: утверждение более ранней даты заменяет версии после неё. Справочники,
общие для исторических снимков, в стандартной админке доступны только для просмотра
и добавления новых записей.

### Работа с таблицами коэффициентов

На глобальной странице и странице подразделения доступны поиск по названию/коду
товара и фильтры по группе планов продаж, группе ERP и бренду. Фильтры только скрывают
строки, не исключая их из сохранения. Режим **Только изменённые** показывает строки
с несохранёнными правками. Сброс фильтров не отменяет изменения.

Изменённые поля подсвечиваются жёлтым; счётчик **Изменено** учитывает также формы
руководителя и добавления товара. Возврат исходного значения снимает подсветку;
переключение между десятичной записью и процентами само по себе не считается правкой.
Можно вводить `0.05`, `0,05` или `5%` — это один коэффициент. Сравнение получает только
действительно изменённые коэффициенты, сохраняя точность остальных значений.

На широком экране закреплённая панель показывает предлагаемую сумму мотивации,
разницу и действия **Сохранить изменения** / **Утвердить**. Разница имеет нейтральный
цвет: её повышение или снижение само по себе не определяет качество решения.
Сохранение в панели относится к основной таблице; руководитель сохраняется отдельно.
При уходе со страницы или действии, которое потеряет правки другой формы,
выводится предупреждение. Сначала сохраните руководительские настройки и варианты
формул, затем утверждайте набор: в предварительное утверждение входят коэффициенты
таблицы и отмеченные удаления товаров.

Создание версии, история, добавление товара и настройки руководителя раскрываются
по нажатию. Импорт, справочники и копирование находятся в меню **Ещё**; настройки
формулы и удаление — в строке бренда. Копирование в подразделения или из глобальной
таблицы предупреждает о замене значений и позволяет отменить действие.

Меню **Подразделения** открывается нажатием или клавишей Enter; поиск сокращает список,
Escape закрывает меню. Таблицы прокручиваются в своей области. На широком экране
товарные колонки закреплены, на узком доступна горизонтальная прокрутка всей таблицы.

### Общая оболочка портала

Главная (`/`), модель закупок и мотивация используют общий шаблон
`base/portal_shell.html`. В шапке находятся только два проекта: **Модель закупок**
и **Мотивация**. Боковое меню показывает страницы выбранного проекта и переход на
главную. На узком экране оно открывается кнопкой **Меню раздела**; Escape закрывает
меню и возвращает фокус на кнопку. Для вошедшего пользователя показывается имя,
для сотрудников с `is_staff` доступна ссылка на стандартную Django Admin.

Система планирования и редактор справочников DWH доступны в блоке **Другие разделы**
на главной. Их собственные страницы и маршруты сохранены. Сценарии закупок, версии
коэффициентов и выбранные планы продолжают использовать существующие механизмы
каждого модуля; общий интерфейс не объединяет эти параметры и не меняет расчёты.

Общий шаблон предоставляет блоки `module_css`, `module_navigation`, `portal_content`
и `module_js`. Базовые шаблоны двух приложений подключают свои формы, стили и скрипты
через эти блоки. Общие стили и переключение мобильного меню находятся в
`base/static/base/portal.css` и `portal.js`. Миграции базы для оболочки не требуются.

### Роли и вход в портал

Все рабочие страницы требуют входа на `/accounts/login/`. Роль назначается
в **Администрирование → Пользователи → Роль в портале** при создании или
редактировании пользователя. Для каждого пользователя выбирается одна роль:

| Роль | Доступ |
| --- | --- |
| Администратор | Оба проекта, остальные разделы и администрирование; все действия |
| Генеральный директор | Только мотивация, все действия внутри проекта |
| Логист | Только модель закупок, все действия внутри проекта |

Для назначения **«Аналитик» модели закупок** используйте «Права по проектам → Модель закупок → Аналитик» в карточке пользователя или группы. Доступны только просмотр и скачивание Excel. Настройки, импорт, экспорт в MS SQL и запуск расчёта закрыты на сервере. Роль независима от аналитика дашбордов; существующие аналитики дашбордов новых прав автоматически не получают. Подробнее: [Роль аналитика модели закупок](docs/purchase-analyst.md).

Существующие активные суперпользователи сохраняют полный доступ. Остальным
пользователям нужно назначить роль; без роли доступ к проектам закрыт.
Роль администратора автоматически даёт доступ к Django Admin. Две роли
одновременно закрывают доступ до исправления назначения. Проверки действуют
также для прямых адресов, POST и API; скрытие пунктов меню не заменяет проверку.
Выход выполняется кнопкой «Выйти» с защитой CSRF.

Если суперпользователя ещё нет, создайте его локально (пароль вводится в терминале):

```powershell
.\.venv310\Scripts\python.exe manage.py createsuperuser --settings=portal.settings_local
```

После обновления запустите `start.ps1` как обычно: миграция создаст группы ролей
без изменения планов, коэффициентов, закупок и существующих паролей. Затем
войдите суперпользователем и назначьте роли сотрудникам.

### Объём контейнера для товара

У каждого товара есть поле **«Объём контейнера, м³»** (`container_volume`).
По умолчанию оно равно **65**, в том числе у существующих товаров после миграции.
Значение можно менять в таблице товаров или отдельной форме редактирования;
оно переносится при копировании сценария и выгружается в `portal.PGGoods` MS SQL.
В Excel новая колонка добавлена в конец. Импорт старого файла без этой колонки
сохраняет текущий объём контейнера; у нового товара используется 65.

### Общие параметры закупок: таможня и доставка

Над таблицей товаров задаются параметры выбранного сценария: цена фрахта,
**таможенная ставка, %** (от 0 до 100) и **стоимость доставки до склада**
(неотрицательная сумма). Для новых параметров значение по умолчанию — 0.
Кнопка «Сохранить» сохраняет все три значения, а копирование из сценария
переносит весь набор. Они выгружаются в `portal.Freight.customs_rate` и
`portal.Freight.warehouse_delivery_cost` с автоматическим добавлением SQL-колонок.
Изменения параметров делают предыдущий экспорт неактуальным.
Добавление параметров само по себе не меняет формулы расчёта закупок.

### Пошлина по товару

У каждого товара есть параметр **«Пошлина, коэффициент»** (`duty_rate`):
**0,1 = 10%**, **0,05 = 5%**, по умолчанию **0**. Значение используется в формуле
напрямую, без повторного деления на 100. В таблице вводится процент (10 для 10%),
в отдельной форме — коэффициент с пояснением 0,1 = 10%. Параметр
копируется между сценариями, выгружается и импортируется как числовой коэффициент
с процентным форматом ячейки Excel.
Значения в базе и файлах автоматически не масштабируются. MS SQL получает тот же
коэффициент в `portal.PGGoods.duty_rate`. Общая таможенная ставка сценария остаётся
процентной: например, 22 означает 22%.

### Расчёт стоимости товаров

Пользователь редактирует только закупку, группу планов продаж, группу товаров,
бренд, вид закупки, объём товара, объём контейнера, пошлину, EXW и запас в днях.
Плановая группа, процент остатка, DDP, KDDP и компоненты стоимости доступны
только для просмотра. Расчётные значения из POST, массового обновления и Excel
игнорируются: окончательные значения рассчитывает сервер.

Все суммы задаются в USD. Пошлина хранится коэффициентом, остальные процентные ставки — как 0–100:

```text
Доля контейнера = объём товара / объём контейнера
Фрахт за товар = доля контейнера × цена фрахта за контейнер
CIF = EXW + фрахт за товар
Таможенный платёж = (таможенная ставка / 100) × CIF × (1 + коэффициент пошлины)
Доставка за товар = стоимость доставки до склада × доля контейнера
DDP = CIF + таможенный платёж + доставка за товар
KDDP = DDP / EXW (при EXW > 0)
```

При EXW = 0 сохраняется предыдущий KDDP. Тип поставки закупки выбирается из
«Прямой контракт», «P2» и «Закупка РФ»; по умолчанию — **P2**.
Для «Закупка РФ» DDP всегда равен EXW. При обновлении прежний признак РФ
сохраняется как этот тип, остальные закупки получают P2.

Общие параметры выбранного сценария также содержат расходы на загран доставку
без DDP (по умолчанию 1100 USD за контейнер) и НР_Таможенный НДС (10%).
Расходы за товар равны доле контейнера × расходы за контейнер.
Для P2 НР_Таможенный НДС за товар равен таможенному платежу × ставке НР / 100;
для остальных типов — 0. Обе суммы отображаются и экспортируются отдельно,
не включаются в DDP.

В разделе **«Группы и пошлины»** задаётся пошлина группы товаров. При выборе
группы она подставляется по умолчанию; пользователь может изменить её у товара.
Изменение справочной пошлины не заменяет сохранённые пошлины существующих товаров.
Миграция заполняет справочник существующими группами, сохраняя индивидуальные
пошлины, и рассчитывает цены по новым формулам. При разных исходных пошлинах
одной группы справочное значение берётся у товара с наибольшим ID.

Изменение общих параметров или типа поставки пересчитывает существующие
товары. Копирование товара использует общие параметры целевого сценария.
Перед экспортом в MS SQL и Excel цены пересчитываются. В SQL автоматически
добавляются компоненты цены и признак РФ; Excel содержит расчётные компоненты
в дополнительных колонках. После обновления нужно повторить экспорт сценариев.
Перед миграциями `start.ps1` сохраняет резервную копию базы в `.local/backups`.

### Копирование коэффициентов из версии и отчёт по плану

На глобальной странице и странице подразделения в панели версий доступно
«Копировать коэффициенты из версии». Цель — последний черновик; дата и статус
не меняются. Глобальная страница заменяет только глобальные коэффициенты,
подразделение — свои коэффициенты и коэффициенты руководителей. Исходная версия
и остальные подразделения сохраняются. Перед заменой требуется подтверждение;
несохранённые правки страницы будут потеряны.

Отчёт по планам продаж получает итоги и списки фильтров одним агрегирующим
запросом. Скрытые уровни дерева создаются в браузере только при раскрытии,
без повторного запроса к серверу. Кнопки «Развернуть всё» и «Свернуть всё»
сохраняют прежнее поведение; CSV включает полный результат по выбранным фильтрам.

### Коэффициенты директоров

Глобальные коэффициенты директоров встроены в общую форму рядом с группами
«Политики» и «Продажи». Индивидуальные настройки встроены третьей группой в общую форму
коэффициентов подразделения.
У директоров один набор K0–K4 по товарной матрице, без разделения на политики
и продажи. Числа вводятся в процентах; например, 1 означает 1%.
В общей таблице значения директоров задаются для строк товарной матрицы;
сохранение этой формы сохраняет все три группы. Старый адрес отдельной
глобальной страницы директоров перенаправляет в общую форму.
На странице филиалов выбираются филиал и сотрудник. Один филиал может иметь
нескольких директоров, каждый со своим набором коэффициентов.

Справочник директоров ведётся вручную: ФИО, уникальный код сотрудника и филиалы.
Добавить или изменить сотрудника можно в раскрываемом справочнике под общей
таблицей подразделения либо в Django admin.
Коэффициенты копируются из глобальных настроек директоров выбранной версии или
из другого набора той же страницы в прошлой версии. Перед заменой требуется
подтверждение. Пустой источник не удаляет текущие значения.

Используются общие версии мотивации: при создании версии копируются оба новых
набора, после утверждения они доступны только для просмотра. Утверждение общей версии применяется ко всем группам и сотрудникам.
Удаление черновика удаляет и его коэффициенты директоров, сохраняя историю
утверждённых версий и справочник сотрудников.

На этом этапе коэффициенты директоров не участвуют в расчёте плана продаж
и не экспортируются в корпоративные таблицы SQL.
После обновления нужно выполнить миграции (start.ps1 делает это автоматически).

### Выбор групп коэффициентов

Переключатели над таблицей позволяют скрыть политики, продажи и директора.
Видимость запоминается в браузере; скрытие не удаляет и не отключает значения
при сохранении. Коэффициенты директора пока не участвуют в сравнении планов.
Перед утверждением нужно сохранить изменённые значения директоров.

На странице подразделения кнопка «Копировать из глобальных» сначала открывает
выбор одной группы: политики, продажи или директор. Для директора дополнительно
выбирается сотрудник филиала. Заменяется только выбранная группа; остальные
группы и директора сохраняются. После копирования директора в общей форме выбран соответствующий сотрудник.

Из общей глобальной формы можно копировать выбранные группы в несколько
подразделений. Выбранный директор должен быть привязан ко всем целевым филиалам.
Источником служат сохранённые значения глобальной версии; несохранённые правки
не копируются. Копирование глобальной формы из версии включает все три группы.

### Общая форма подразделения и директора

Над таблицей подразделения выбирается сотрудник-директор. Политики и продажи
принадлежат филиалу, группа «Директор» K0–K4 — выбранному сотруднику. Пока
сотрудник не выбран, вместо его ячеек показывается подсказка. Все три группы
можно скрывать. Общая кнопка сохранения записывает общие и выбранные личные
коэффициенты атомарно. Ошибка в директорских значениях отменяет всё сохранение.

При смене сотрудника с несохранёнными правками требуется подтверждение.
Кнопка «Копировать другому директору» заменяет только личный набор получателя
сохранёнными значениями текущего сотрудника в той же версии и филиале.
Источником не могут быть пустой набор или сотрудник другого филиала.
Копирование из версии сохраняет других сотрудников и включает выбранного
директора. Смена и создание версии сохраняют выбор сотрудника.

Отдельная страница директоров убрана из меню; прежние ссылки перенаправляют
в общую форму подразделения. Справочник сотрудников находится под таблицей.
Изменений схемы данных в этом объединении нет.

### Отчёты мотивации в Django

В меню мотивации добавлен раздел «Отчёты» с тремя нативными страницами:
«Мотивация менеджера», «Факт закрытых сделок», «Мотивация по подразделениям».
Они повторяют оформление подготовленных RDL и читают те же источники DataWH
через существующее подключение DWH_SQL_CONN_STR. SSRS для показа страниц не нужен.

Есть параметры, сводные суммы, раскрытие групп, детализация по товарной матрице
и красивые числа без копеек. На странице сделок — пагинация по 50 строк,
дополнительные поля по переключателю и CSV текущей страницы. На странице
менеджера «Подразделение» свёрнуто по умолчанию. Ключевые показатели мотивации
по филиалам выделены цветом.

Для списков с несколькими значениями пустой выбор означает «Все». После выбора
типа и филиала обновите справочные списки сотрудников. Отчёты доступны
администратору и генеральному директору; логисту доступ запрещён. При отсутствии
подключения показывается понятное сообщение, без технической страницы ошибки.

Определения запросов и проверенных формул: admin_motivation/sql/reports/README.md.
Перед использованием сверяйте с SSRS на одинаковых фильтрах: живой DataWH
не был доступен в среде разработки. Изменений схемы базы портала нет.

### Обновление полей справочника товаров

На странице «Товары» кнопка **«Обновить справочник товаров»** загружает из
`ModelPurch.dbo.PlanningGroupOZP` группу планов продаж, группу товаров и марку
для всех существующих товаров выбранного сценария (независимо от
фильтров страницы). Подключение: `MS_SQL_CONN_STR`. Сопоставление по плановой группе
не учитывает регистр и пробелы по краям. Новые товары не создаются, отсутствующие
в источнике остаются без изменений; показываются количества обновлённых, неизменных
и ненайденных товаров. При дублях выбирается целая строка с приоритетом ключа `PG%`, затем по ключу и значениям полей; порядок строк источника не влияет на результат.
Поставщик, ручные параметры закупки и расчётные цены DDP сохраняются.
Сначала сохраните изменения таблицы:
при наличии несохранённых правок кнопка обновления недоступна.

Перед чтением справочника эта же кнопка пересоздаёт таблицу
`ModelPurch.dbo.PlanningGroupOZP` запросом из
`model_purch/sql/refresh_goods_directory.sql`: источник `DataWH.planning.Goods`,
объём из `DataWH.dbo.ModelCodeERP`, признак плана из `ModelPurch.dbo.GoodsPlan`.
На плановую группу выбирается одна строка с приоритетом ключей `PG%`.
Пересоздание и чтение выполняются в одной транзакции MS SQL; при ошибке SQL
или проверки источника выполняется rollback. Одновременные нажатия сериализуются
через `sp_getapplock`. Подключению нужны права на пересоздание таблицы и чтение
источников. Успешный SQL-этап фиксируется перед обновлением локального сценария;
ошибка локального этапа откатывает изменения товаров, но не уже обновлённую SQL-таблицу.

### Загрузка блоков коэффициентов директоров

В разделе коэффициентов (глобальных и подразделения), в «Ещё: импорт, копирование
и справочники», доступна кнопка **«Загрузить коэффициенты директоров»**.
Она открывает загрузку в выбранную на исходной странице версию; название версии
в Excel не определяет получателя. Запись разрешена только в последний черновик.

Формат: лист «Коэффициенты», товарные колонки «№», «Группа планов продаж»,
«Группа ERP», «Марка / бренд», затем блоки из пяти колонок K0–K4. Над каждым
блоком — по одному ФИО на строку в его первом столбце. Каждый блок применяется
ко всем указанным над ним директорам и их привязанным подразделениям. Совпадение
ФИО и товарной матрицы не учитывает регистр и лишние пробелы; неоднозначные
совпадения, неизвестные сотрудники/товары и отсутствие привязок отменяют весь импорт.
Глобальные коэффициенты, политики, продажи и привязки сотрудников не меняются.
Пустая пятёрка сохраняет предыдущие значения; частично заполненная — ошибка.
Допускаются числа от -1 до 1 и строки с процентами; округление до шести знаков.
Формулы в коэффициентах нужно сохранить как значения. Повторное ФИО внутри одного
блока учитывается один раз; повтор между блоками требует исправления файла.
После загрузки показываются количества директоров и созданных/обновлённых/неизменных
строк. Лимит файла — 5 МБ, после распаковки — 30 МБ.


### Фоновая работа в Windows без IIS

После первоначальной настройки окружения портал можно запускать без открытого окна
PowerShell. Права администратора не нужны. Работает под текущей учётной записью
Windows с её доступом к MS SQL и доменам. Сначала остановите старый запуск `start.ps1`
через Ctrl+C: скрипт намеренно не завершает неизвестный процесс, занимающий порт.

Первый запуск из папки проекта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\portal.ps1 start -Database .\db.sqlite3 -BindAddress 0.0.0.0 -Port 8000
```

Одна команда для обновления из Git и перезапуска:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\portal.ps1 restart -Update
```

Без обновления кода: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\portal.ps1 restart`.
Для проверки замените `restart` на `status`, для остановки — на `stop`.
Адрес, порт и явно выбранная база сохраняются в `.local/background-settings.json`;
если база не указана, используется обычная настройка `start.ps1`.
Скрипт использует `.venv310` или `.venv`, обновляет зависимости при `-Update`,
затем обычный `start.ps1` применяет миграции и собирает статику.
Git обновляется только fast-forward и без локальных изменений: при конфликте
обновления работающий портал не останавливается. Ошибка установки зависимостей
или подготовки после остановки требует исправления и повторного `start`.

Логи каждого запуска: `.local/portal-*.log`; точный путь выводит `status`.
Он показывает состояние процесса, а не проверяет доступность MS SQL или отчётов.
Если подготовка занимает более 45 секунд, скрипт сообщает об этом и оставляет её
работать: следите за логом, не запускайте второй экземпляр.

Окно PowerShell можно закрыть. При выходе из учётной записи Windows или перезагрузке
фоновый процесс остановится; это не служба Windows и не автозапуск.
После входа выполните `portal.ps1 start` приведённым выше способом.
Используется текущий сервер Django, как в `start.ps1`.
Доменные настройки и строки подключения задавайте сохранёнными переменными Windows
либо в сеансе, из которого запускаете команду. Только временные переменные из другого
закрытого окна PowerShell при перезапуске не восстановятся.


### Запуск через Планировщик Windows (рекомендуемый вариант)

`portal-task.ps1` создаёт отдельное задание `PortalComp`, запускающее существующий
`start.ps1` с подготовкой базы, миграциями и статикой. Закройте старый ручной запуск
через Ctrl+C; старый фоновый запуск при необходимости остановите `portal.ps1 stop`.
Не используйте два способа запуска одновременно.

Создание задания один раз (работает, пока пользователь вошёл в Windows):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\portal-task.ps1 install -Database .\db.sqlite3
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\portal-task.ps1 start
```

Для запуска при включении компьютера и работы после выхода из учётной записи добавьте
к команде **install** параметр `-RunWhenLoggedOff`. Откроется стандартный запрос
пароля текущей учётной записи Windows. Пароль не записывается в файлы проекта;
его хранит Планировщик. Такой режим может требовать разрешения администратора
и права «Вход в качестве пакетного задания» согласно политике домена. По умолчанию
используется обычный уровень прав, без повышения. При смене доменного пароля обновите
учётные данные задания в Планировщике. Установка не запускает портал автоматически.

Обновление и перезапуск одной командой:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\portal-task.ps1 restart -Update
```

Без обновления уберите `-Update`. Другие действия: `start`, `stop`, `status`.
Если Git не может обновиться без слияния или есть локальные изменения, работающее
задание не останавливается. После остановки устанавливаются зависимости; ошибки pip
или подготовки нужно исправить и выполнить `start` повторно. Не обновляйтесь во время
длительного расчёта: остановка задания прерывает его работу.

Задание не ограничено стандартными тремя днями выполнения и пробует перезапускаться
до трёх раз с интервалом в минуту при сбоях. `status` показывает статус задания и
LastTaskResult (0 — нормальное завершение, 267009 / 0x41301 — сейчас выполняется).
Подробный общий лог, включая ошибки подготовки: `.local/portal-task.log`.
Состояние Running означает работающий процесс, а не успешное соединение с MS SQL.
База и параметры сохраняются в `.local/task-settings.json`; значения по умолчанию:
`0.0.0.0:8000`. Все скрипты запуска предназначены для Windows PowerShell 5.1.

Если задание с таким именем уже существует, установка его не заменяет. Используйте
другое имя через `-TaskName` (его нужно передавать и в последующих командах) либо
сначала разберитесь с существующим заданием в Планировщике.


Локальный запуск собирает статику в `.local/static`, вне отслеживаемых Git файлов.
Если старый запуск уже изменил `static/admin`, `static/django_extensions` и создал
другие папки внутри `static`, сохраните их перед первым обновлением:

```powershell
git stash push --include-untracked -m "Generated static before update" -- static
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\portal-task.ps1 restart -Update
```

Это сохраняет изменения только внутри `static`; исходники приложений и база не
затрагиваются. Сохранённые файлы доступны через `git stash list`; возвращать
старую собранную статику после обновления не требуется. Если остаются другие
локальные изменения, проверьте их отдельно через `git status --short`.

SQLite при запуске через `start.ps1` переводится в WAL; ожидание блокировки — до
30 секунд. WAL уменьшает конфликты между чтением и записью, но одновременно
записывать всё равно может только один процесс. Не запускайте второй экземпляр
портала и не держите открытую транзакцию редактирования в SQLite-редакторе.
Не удаляйте `db.sqlite3-wal` / `db.sqlite3-shm` вручную. Резервную копию работающей
базы делайте SQLite backup API; для обычного копирования файла остановите все
процессы, использующие базу. Носитель SQLite должен быть локальным, не сетевой папкой.


### Сегменты скидок мотивации

Администратору доступен раздел «Мотивация → Сегменты скидок». Для каждого типа
скидки задаются пороги O0–O4 (латинская буква O). Значения — процентные пункты:
10 означает 10%, пустое поле означает SQL NULL. Тип скидки не может повторяться
в одной версии; непустые пороги должны быть в диапазоне 0–100 и не убывать.
Все пять порогов могут быть пустыми, например для NO_DISCOUNT или PROJECT.

Используется та же GlobalCoeffVersion, что у коэффициентов. Редактируется только
последний черновик; история доступна для просмотра. При создании новой версии
пороги копируются автоматически. Изменения сегментов обновляют ревизию версии
и отменяют ранее подготовленное подтверждение утверждения. Утверждение выполняется
через глобальные коэффициенты; окно подтверждения включает список сегментов.

Первоначальное заполнение: раскройте «Первоначальная загрузка из MS SQL» и нажмите
«Загрузить недостающие версии из MS SQL». Читается
DataWH.motivation.SegmentMotivation (Date_, TypeDiscount, O0–O4). Для каждой даты
версии выбирается последний действующий на эту дату набор. Заполняются только
пустые версии, включая исторические; существующие локальные настройки не
перезаписываются. Источник MS SQL при импорте не изменяется. Если данные источника
неполны, содержат дубли или некорректные пороги, импорт целиком отменяется.

Общая выгрузка настроек включает SegmentMotivation: вся утверждённая цепочка
записывается с исходными effective_from, черновики и заменённые версии исключены.
Замена начиная с первой утверждённой даты и вставка сегментов выполняются в одной
SQL-транзакции с остальными коэффициентами; при ошибке всё откатывается.
До первоначального заполнения, пока ни в одной утверждённой версии сегментов нет,
выгрузка сохраняет прежнюю SQL-таблицу без изменений. Если заполнена только часть
утверждённых версий, экспорт блокируется до загрузки недостающих.

После обновления start.ps1 применит миграцию 0019_discountsegment автоматически.
SQL-экспорт и первоначальное чтение используют существующее подключение DataWH;
для новой таблицы чтения и записи нужны соответствующие права. Проверки в разработке
используют имитацию SQL Server, рабочие данные не изменяются.

Перед миграциями большой SQLite запуск может долго находиться на резервном
копировании: сервер начинает слушать порт только после копии и её проверки.
В журнале выводятся `Backup copy: ...%`, ожидание блокировки SQLite и отдельный
этап `Backup integrity check running`. Проверка целиком читает созданный файл;
100% копирования ещё не означает завершённую проверку. Не запускайте второй
экземпляр и не повторяйте restart, пока резервирование продолжается.
`portal-task.ps1 status` показывает статус задания и последние строки журнала.


### Пилот: выполнение плана подразделения и массовая формула

В настройках товара доступна формула «Подразделение(Глобально)». Она использует
выполнение плана всего подразделения (включая объединённые источники) за тот же
год и квартальный/годовой период, по соответствующему виду работника. В сумму
подразделения входят и товары/авторы с другими формулами. Личный объём, ставки
K0–K4 и имеющиеся правила выплаты/порогов сохраняются. Плановая мотивация остаётся
суммой личного/планового объёма × коэффициент: процент выполнения применяется
при фактическом расчёте мотивации в SQL.

На глобальной странице и странице филиала раскройте «Применить формулу к нескольким
товарам». Отметьте товары в первом столбце или используйте «Выбрать видимые товары»
после фильтрации. Выберите формулу и группы «Политики»/«Продажи», затем примените.
Настройка изменяет только выбранную версию и текущую область; проценты не меняются.
Глобальные настройки для пилота нужно скопировать в требуемые филиалы обычным
действием копирования. Для пилота только Д-Москвы удобнее редактировать её страницу.
Сначала сохраните другие правки таблицы: массовая операция не сохраняет их автоматически.

Период действия определяется датой общей версии коэффициентов. После пилота
верните обычную формулу в следующей версии. Утвердите версию и выгрузите её в DWH.
При наличии утверждённых коэффициентов филиала с пилотной формулой выгрузка также
подготавливает PortalCalcBySub в той же SQL-транзакции. Источник sp_CalcBySub не
меняется. Расчёт запускайте из портала/SQL Agent через PortalCalcBySub. Если структура
живой процедуры не распознана, операция отменяется; несовместимая формула не
подменяется молча обычной. Подготовка проверена на сохранённых вариантах процедуры,
но рабочий SQL Server в среде разработки недоступен.

### Возврат последней утверждённой версии в черновик

Администратор может выбрать последнюю утверждённую версию и раскрыть действие
«Вернуть последнюю утверждённую версию в черновик». Требуются причина, подтверждение
и актуальная ревизия. Если существует более новый черновик, сначала сохраните нужные
изменения или удалите его штатным действием. Старую утверждённую версию вернуть нельзя.

Перед возвратом сохраняется JSON-снимок коэффициентов всех областей и сегментов
скидок, дата утверждения, автор действия и причина. Скачать снимок можно из журнала
возвратов. Версии, заменённые этим утверждением, восстанавливают статус «Утверждена».
Прежние записи утверждений и утверждённые снимки расчётов сохраняются. Старые суммы
и уже выгруженные данные MS SQL не отзываются автоматически. После исправления
повторите утверждение, выгрузку и расчёт. Если утверждённых версий не осталось,
выгрузка заблокирована до нового утверждения.

### Удаление директора

В справочнике директоров в колонке «Действия» администратору доступно «Удалить».
Удаление требует подтверждения и возможно только при отсутствии ссылок из
коэффициентов. Используемый директор и история его расчётов сохраняются; его
текущие филиалы можно изменить через обычное редактирование.

### Подтверждение готовности после перезапуска

`portal-task.ps1 start` и `restart -Update` ждут успешного HTTP-ответа страницы входа
(до 30 минут), показывая последние этапы из лога каждые 15 секунд.
Обновлять браузер можно после зелёного сообщения `PORTAL READY - HTTP OK`.
Если время ожидания вышло, фоновая задача остаётся запущенной: сначала проверьте
`portal-task.ps1 status`, не запускайте второй экземпляр. Проверка выполняется
с самого сервера и не подтверждает доступность сети с других компьютеров.

Удаление директора из справочника требует подтверждения администратора. Если
коэффициентов нет, запись удаляется. Если коэффициенты есть, директор скрывается
из действующего справочника и теряет привязки к филиалам; исторические коэффициенты,
код сотрудника и утверждённые выплаты сохраняются. Это действие само по себе
не изменяет утверждённые версии и не выполняет экспорт в MS SQL.

### Роль группы и роль пользователя

В группах доступа выбирается та же «Роль в портале», что в карточке пользователя.
Роль «Продажи» даёт личные отчёты продаж с ограничением по точному ФИО автора,
как «Политик» для политиков. Зам. директора видит всех политиков разрешённых
подразделений, Директор — всех работников выбранных филиалов. Для этих четырёх
ролей подразделения обязательны. Для Администратора, Генерального директора
и Логиста сохраняется прежний доступ соответствующей роли; выбранные
подразделения его не ограничивают.

Пустая роль в карточке означает наследование роли выбранных групп. Несколько
групп с одной ролью объединяют подразделения. Разные наследуемые роли дают
конфликт и отсутствие доступа; администратор может выбрать роль пользователя
явно. Явная роль имеет приоритет над наследуемой. При обновлении существующие
группы сохраняют прежнюю роль «Политик» и прежние типы данных отчётов, чтобы
не расширить и не потерять существующий доступ. Нужную новую роль им можно
назначить на странице групп. Новые группы определяют тип данных по роли,
без отдельного выбора «Вида работника».

Заместитель директора дополнительно видит собственную директорскую премию:
в Дашборде, Детальном отчёте и Факте закрытых сделок выберите «Директора».
Подразделения ограничены группами доступа, автор жёстко закреплён за ФИО
из карточки пользователя (Фамилия + Имя и отчество). Подсказки и выгрузки
используют то же ограничение. В режиме «Политики» по-прежнему доступны все
политики разрешённых подразделений. Если в карточке не заполнены имя или
фамилия, директорская часть не открывается; доступ к политикам сохраняется.

В роли «Директор» доступны только три отчёта: Дашборд, Детально и Факт закрытых
сделок. В них сохраняется доступ ко всем работникам разрешённых филиалов.
Сводный отчёт по плану и отчёт по подразделениям остаются у администратора
и генерального директора.

В «Расчёт и задания» задаются год факта, версия плана MS SQL и квартальная/годовая
доли в процентах (сумма строго 100%). В списке доступны только версии планов, уже загруженные на портал и не удалённые
из рабочих списков. В MS SQL передаётся исходное название выбранной версии.
Для существующего задания откройте «Изменить параметры и расписание», сохраните
и нажмите «Запустить сейчас». Параметры сохраняются в шаге SQL Agent и работают
по расписанию независимо от портала. Старым заданиям год и план автоматически
не присваиваются: перед новым запуском их необходимо настроить. Уже созданные
расписания SQL Agent миграция не меняет; сохраните задание для обновления шага.
Нужна процедура sp_CalcBySub с параметрами FactYear, PlanVersion, QuarterShare,
YearShare. Неподдерживаемая процедура или отсутствующая версия плана блокируют
синхронизацию, сохраняя прежний шаг SQL Agent. Исходная процедура не изменяется.

На странице «Расчёт и задания» статусы и история обновляются каждые 10 секунд
без перезагрузки и потери несохранённых полей. На скрытой вкладке опрос
приостанавливается. В карточке раскройте «История запусков»: последние 30
завершённых запусков SQL Agent, начало (МСК), длительность, результат и сообщение.
Ошибка подключения помечает данные как устаревшие, сохраняя последний результат.
История хранится в msdb SQL Server Agent и ограничена его настройками очистки;
портал не создаёт вторую копию журнала. Для перевода времени используется
текущее смещение SQL-сервера, как у расписаний (сервер без сезонного перевода).
Мониторинг доступен только администратору и не запускает расчёт повторно.

### Порог выплаты и поправки подразделений

В задании есть отдельный порог выполнения плана (коэффициент 0..1, по умолчанию
0.8 = 80%). Он не связан с квартальной долей 80% и годовой долей 20%.
Портал параметризует только распознанные условия выплаты в своей копии процедуры;
неизвестная структура блокирует подготовку вместо запуска с неподдерживаемыми правилами.

«Коэффициенты руководителя» — множители сумм мотивации подразделения для всех
работников, включая директоров. 100% = ×1, 90% = ×0.9. Квартальные и годовая
поправки применяются к возможной и доступной мотивации USD/RUR и факту сделок.
Планы, отгрузки, проценты выполнения и ставки K0–K4 не меняются. Годовая доплата
вычисляется из уже скорректированных квартальных сумм и повторно не умножается.
Поправка берётся из последней утверждённой выгрузки с Date_ не позже конца
соответствующего квартала/года; при отсутствии значения действует ×1.

Администратор может менять только эти поправки непосредственно в утверждённой
версии: обязательны причина, подтверждение и актуальная ревизия страницы.
Журнал хранит пользователя, время, период, прежнее и новое значение. Другие
коэффициенты утверждённой версии остаются заблокированы. После правки требуется
выгрузка в MS SQL и пересчёт; готовые результаты автоматически не переписываются.
Правка прошлых периодов может изменить их при пересчёте, о чём требуется подтверждение.
Экспорт поправок и подготовка совместимой процедуры выполняются одной транзакцией.

После создания и проверки новой резервной копии SQLite портал автоматически
оставляет три последние копии этой базы и удаляет более старые. Текущая
проверенная копия дополнительно защищена от удаления. Очистка касается только
файлов стандартного вида `db-YYYYMMDDTHHMMSSffffffZ-xxxxxxxx.sqlite3` в `.local/backups`
(префикс соответствует имени базы); рабочая база, файлы других баз, ссылки и
копии с произвольными именами не удаляются. Если копирование/проверка не удались,
очистка не запускается. Заблокированный файл пропускается с записью в журнал.

Массовая формула поддерживает группу «Директор». В глобальном разделе меняются
глобальные директорские строки, в подразделении — только строки выбранного
активного директора, привязанного к этому филиалу. K0–K4 сохраняются. Если
для какого-либо отмеченного товара ставки директора не сохранены, всё действие
отклоняется без создания нулевых ставок. Формула сохраняется в версии, копируется
между версиями/директорами и выгружается в MS SQL. При отсутствии явной формулы
сохраняется прежний выбор по группе товара. Настройки политиков и продаж независимы.

Создание/копирование/история версий собраны справа от выбора версии; раскрытые
панели закрываются по Escape и клику снаружи. Переключатели вариантов сравнения
и пояснение находятся в строке параметров сравнения.

В таблицах коэффициентов действия собраны в общей компактной панели: добавление
товара, массовая формула, копирование между группами и подразделениями, импорт и
справочники. Кнопки раскрывают одну форму за раз; закрытие панели сохраняет введённые
значения. Импорт остаётся связан с исходной формой коэффициентов.

Удалённые (архивные) директора исключаются из выбора сотрудника в коэффициентах,
даже если в версии остались их исторические строки. Прямая ссылка на удалённого
сотрудника показывает предупреждение; сохранение из старой вкладки запрещено.
Сами исторические строки и результаты расчётов не удаляются.

Сохранение ставок и поправок проверяет область редактирования и ревизию версии,
затем повторно читает отправленные значения из БД внутри той же транзакции.
Несовпадение отменяет всю операцию. Сообщение результата различает сохранённые
изменения (с количеством полей), отсутствие новых изменений и ошибку. Выгрузка в
MS SQL и пересчёт по-прежнему выполняются отдельно.

Меню мотивации: планы продаж → сегменты скидок → глобальные коэффициенты →
подразделения → отчёты → выгрузка в DWH → справочники. Список подразделений для
навигации берётся общим шаблонным тегом из активных подразделений; страница
сегментов и другие страницы больше не обязаны передавать его отдельно.

Мотивация: единый рабочий маршрут показывает состояние утверждённых настроек,
рабочую версию, область и следующий шаг. Новый журнал выгрузок содержит снимок
версий и справочников. Отметка «актуально» появляется только при совпадении
снимков; черновики не выдаются за выгруженные данные.

Новые SQL Agent шаги регистрируют фактические параметры, время и использованный
снимок выгрузки в `motivation.PortalMotivationRun`. Метаданные выгрузки пишутся в
`motivation.PortalMotivationExport` в той же SQL-транзакции, что и коэффициенты.
Выгрузка и расчёт используют общий applock. Портал получает сведения при проверке
задания и хранит локальную копию для отчётов. Старые запуски не реконструируются:
показывается «не подтверждено». После обновления нужно один раз сохранить
параметры существующих автоматических заданий; ручной запуск обновляет шаг сам.
Объекты журнала создаются при выгрузке/сохранении задания с теми же правами создания
объектов схемы motivation, которые требуются подготовке расчёта.

Завершённый запуск открывает детальный отчёт с годом из журнала и выбранным
подразделением. План показан как параметр запуска: изменение фильтров не запускает
пересчёт. Отчёты читают текущие таблицы; ссылка на старый запуск не создаёт
историческую копию отчёта. Несовпадение настроек, старой ссылки или года отмечается
предупреждением. Запуски вне портального SQL Agent шага не подтверждаются журналом.

Таблица коэффициентов имеет сворачиваемые группы, закреплённые колонки и заголовки,
боковую панель настроек товара и объяснения формул, ставок и поправок. Массовая
формула проверяется сервером без записи; подтверждение связано подписью с
пользователем, ревизией и точным выбором на 15 минут. После ошибки сохранения
введённые значения восстанавливаются, а неверные поля отмечаются. Архив директоров
отделён от действующих записей и доступен только для просмотра.

Роль **«Смотрящий»** даёт полный просмотр проекта «Мотивация» без ограничения по
подразделениям и авторам: планы, версии, коэффициенты, сегменты, справочники,
архивы, задания, история и все отчёты. Назначается в карточке пользователя или
через группу. Прав администратора и доступа к модели закупок эта роль не даёт.

Изменяющие запросы мотивации блокируются middleware независимо от состояния
кнопок. Единственный разрешённый POST — сравнение сохранённых данных без правок,
удалений или утверждения. GET-фильтры и скачивание отчётов доступны; выгрузка
настроек в MS SQL, импорт, пересчёт, запуск заданий и управление пользователями
запрещены. Мониторинг для смотрящего читает журнал запусков без записи наблюдений
в локальную БД. Поля изменяющих форм отключены серверными fieldset и интерфейсом.

После исправления единиц пошлины ранее выполненные экспорты сценариев помечаются
неактуальными. Перед расчётом закупок повторите экспорт сценариев в MS SQL: цены
пересчитаются автоматически. История прежних снимков сохраняется.


Вкладка товаров постоянно показывает все поля: классификацию, закупочные
параметры, план и факт DDP и объёма, DDP стока (USD/шт.), KDDP, составляющие стоимости и дополнительные
расходы. Компактного режима и скрытия столбцов нет.
«Как рассчитана стоимость» раскрывает формулу и используемые количества.
Пошлина в таблице вводится в процентах (10 означает 10%); внутри системы и API
остаётся коэффициентом 0,1. Excel хранит тот же коэффициент, но отображает
его процентным форматом: 10%. При редактировании Excel вводите `10%`, а не `10`.
Старые файлы с коэффициентом 0,1 импортируются без преобразования.


Новые отчёты мотивации: переключатель между доступными отчётами сохраняет общие
условия (год, расчёт, периоды, виды и подразделения), но не переносит личный
предпросмотр, автора сделки, товарную детализацию, поиск и экспорт. Если отчёт
уже сформирован, переключатель сразу запрашивает выбранный отчёт с общими
условиями. При изменении
фильтров показывается предупреждение: суммы и Excel остаются результатом прежних
условий до нажатия «Показать». Кнопка «Вернуть условия отчёта» отменяет выбор.
В «Моей премии» есть переходы к периодам, целям и товарам. В командном отчёте и
реестре сотрудник закреплён при горизонтальной прокрутке, а итоговая строка
показывает суммы по всем страницам, включая нераспределённые строки. Годовая премия
в столбцах названа явно и не включает квартальные премии. Формулы и права доступа
не менялись; старые отчёты остаются на своей вкладке.


Боковое меню портала можно скрыть и вернуть кнопкой в верхней панели.
Освободившееся место занимает содержимое страницы. Выбор сохраняется в браузере
между разделами; для широкого и мобильного экрана состояния независимы.
Клавиша Escape внутри меню закрывает его и возвращает фокус на кнопку.


«Обновить справочник товаров» в модели закупок обновляет классификацию существующих
строк и добавляет отсутствующие группы с положительным количеством в прикреплённых
планах продаж за период сценария. Названия планов и даты передаются SQL-параметрами.
Если группа есть в плане, но отсутствует в справочнике DWH, создаётся строка
с её названием и незаполненными параметрами для проверки.
Повторное нажатие не создаёт дубли; другие сценарии и параметры существующих товаров
не перезаписываются. Новые товары получают поставщика, объём и классификацию из
справочника DWH, вид «Закупается», контейнер и пошлину из группы товаров, EXW и запас
в днях — 0. После добавления нужно проверить параметры, заполнить EXW, обновить
план/факт/сток отдельной кнопкой и повторить экспорт сценария. Без прикреплённых
планов обновляется только классификация существующих товаров; выводится пояснение.


DDP стока в модели закупок = `SUM(s.DDP_USD) / SUM(s.Количество * mce.FlagAccountingQtyBA)`.
В стоимость и объём входят все строки стока группы. Флаг применяется только к
количеству учётных единиц; строки внутренних блоков из стоимости не исключаются.
При неположительном количестве стоимость единицы не определяется. После обновления
кода нужно повторно загрузить «Параметры из плана», чтобы заменить сохранённые
значения DDP стока; затем повторить экспорт сценария перед расчётом.


В каждой строке товаров есть ссылка «Проверить источники». Проверка только читает
DWH для выбранной группы, периода и прикреплённых планов сценария. Она отдельно
показывает план ERP, план первоначальной загрузки, сток себестоимости, наличие/путь
на складах продажи и ожидаемые поступления с теми же правилами даты, что при
первоначальной загрузке. Выводятся количество без флага, учётное количество,
доступная сумма DDP и стоимость учётной единицы. Даты передаются строками ISO для
старого ODBC-драйвера. Аналитик может выполнять проверку. Архивные сценарии
недоступны. Ошибка источника не выдаётся за отсутствие товара. Историческую
причину добавления проверка не восстанавливает, товар и параметры не меняет.


После создания сценария модель закупок открывает его таблицу товаров и рекомендации:
общие параметры (скопировать или обновить), параметры товаров (копирование, ручное
заполнение, импорт Excel, добавление новых из плана), затем загрузка плановых,
фактических и складских показателей за период нового сценария. Копирование товаров
не заменяет свежую загрузку показателей. Рекомендации сохраняются в сессии отдельно
для каждого сценария до нажатия «Скрыть рекомендации»; их можно открыть снова из
панели товаров. Действия запускаются только пользователем, отметки о выполнении
автоматически не выставляются. При сбое первоначальной синхронизации созданный
сценарий тоже открывается в товарах с предупреждением и рекомендациями.
