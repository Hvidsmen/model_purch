# Мониторинг сплитов в DA портале

Пятый проект верхнего меню — **Мониторинг сплитов**. Он открывает `/split-monitoring/` в отдельной вкладке с оригинальным интерфейсом приложения bse-sb/Split-monitoring. Вход, права и доступ к API/снимкам обеспечивает Django-портал. Сборка и расчёты переданного приложения сохраняются; iframe, изменение React/runtime и пересборка не нужны.

## Установка на текущем Windows-сервере

После обновления портала сохраните полный приватный `rac-line-card-portal-private.zip` на сервер. Из корня портала выполните:

```powershell
cd "C:\Users\ETLadmin\Desktop\Python\PortalComp\pythonProject1\model_purch"
powershell.exe -NoProfile -File .\scripts\install_split_monitoring.ps1 -PackagePath "C:\ПУТЬ\rac-line-card-portal-private.zip" -PortalOrigin "http://192.168.221.178:8000"
```

Если не указывать `-PackagePath`, скрипт откроет окно выбора ZIP. Скрипт использует `.venv310`, затем `.venv` того же портала, устанавливает необходимый Waitress 3.0.2, проверяет состав/контрольные суммы пакета и сборки и размещает код и данные в `.local/split-monitoring/`. Для другой схемы/домена/порта укажите реальный адрес портала; для нескольких разрешённых адресов параметр `PortalOrigin` принимает массив. Нужен именно **полный приватный пакет**, а не ZIP исходников GitHub.

Откройте пятую ссылку. Первый авторизованный запрос запустит отдельный backend на `127.0.0.1:8767`; дополнительный сайт IIS, внешний порт и отдельный пароль посетителей не нужны. Процесс использует ту же учётную запись и Python, что и портал, и автоматически запускается снова при следующем обращении после сбоя/перезагрузки. Межпроцессные файловые блокировки предотвращают запуск нескольких backend одновременно.

Данные и архив в Git не добавляются. Рабочие снимки находятся в `.local/split-monitoring/data/`, код релиза — в `releases/<SHA256>/`, конфигурация — в `runtime.json`, журнал — в `backend.log`. Веб-раздача этих каталогов запрещена: gateway отдаёт только защищённый интерфейс/статические файлы `app/dist` и разрешённые API. На Windows каталог должен быть доступен только служебной учётной записи портала и администраторам. Существующие рабочие снимки при повторной установке сохраняются.

## Права

В карточках пользователей и групп добавлен отдельный проект «Мониторинг сплитов»:

- **Аналитик** — интерфейс, исходные снимки, фильтры, расчёт локального сценария, экспорт из приложения.
- **Администратор** — те же действия, обновление из базы и отдельная кнопка «Обновить из GitHub».

Общий администратор портала видит проект автоматически. Прежняя роль «Аналитик» в дашбордах доступа к новому проекту не даёт. Персональный запрет приоритетнее группового разрешения. Режим просмотра от другого пользователя допускает только чтение/расчёт карточки; обновление снимка в этом режиме запрещено.

`/card-api/*` — совместимый с оригинальной сборкой API, тоже закрытый правами портала. POST разрешён только с точным Origin текущего портала и JSON размером до 20 КБ. Обновление снимка дополнительно требует администратора проекта. Cookies/заголовки авторизации портала и управляющий токен не передаются backend из внешних запросов. Его служебный endpoint остановки gateway не проксирует.

## Данные и SQL

Первое открытие использует **сохранённые снимки из переданного пакета**, а не сегодняшний свежий SQL-факт. Их даты/версии показываются самим приложением. Кнопка «Обновить из базы» читает источники Planning(SB)/Sales от служебной учётной записи портала; доступ к DWH и SQL Driver проверяются на корпоративном сервере. Эта интеграция не запускает ETL Sales и не изменяет мотивационные коэффициенты, планы или расчёты.

При необходимости задайте `LINE_CARD_CONNECTION` в окружении процесса портала до его запуска. Пример для Windows-аутентификации:

```text
DRIVER={ODBC Driver 17 for SQL Server};SERVER=vm-dwh;DATABASE=Planning(SB);Trusted_Connection=yes;APP=LineCard-readonly
```

Для обновления нужны SELECT на перечисленные в инструкции приложения объекты Planning(SB)/DataWH. Пароли не вводятся в браузере и не сохраняются скриптом установки. После изменения окружения перезапустите backend, чтобы он получил новые значения.

## Обслуживание

Из корня портала, тем же Python:

```powershell
.\.venv310\Scripts\python.exe .\scripts\split_monitoring_runtime.py status
.\.venv310\Scripts\python.exe .\scripts\split_monitoring_runtime.py stop
.\.venv310\Scripts\python.exe .\scripts\split_monitoring_runtime.py start
```

При `.venv` замените путь Python. `stop` посылает команду только нашему loopback backend с локальным управляющим токеном; чужие процессы по PID не завершаются. Установщик перед заменой пакета останавливает предыдущий backend. После ручной остановки новый запрос к разделу снова запускает его. Состояние 503 не мешает остальному порталу; администратор увидит подсказку по установке/журналу.

Альтернативный путь конфигурации задаётся серверной переменной `SPLIT_MONITORING_CONFIG`. Отдельный запуск самого приложения через его исходный `portal_wsgi.py` остаётся возможен по инструкции авторов.

## Проверки

Есть тесты прав, наследования/отказа, JSON Origin/CSRF, приватности снимков/заголовков и проверки архивов. Дополнительный Chromium-тест открывает реальный полный пакет через пятую ссылку, получает карточку и метаданные, переключает сохранённый Excel-источник и проверяет отказ анонимному клиенту. Включение: `RUN_BROWSER_TESTS=1`, `SPLIT_MONITORING_TEST_PACKAGE=<путь к приватному ZIP>`, `PLAYWRIGHT_CHROMIUM_EXECUTABLE=<путь Chromium>`.

Проверки используют снимок пакета; корпоративный SQL/обновление из базы подтверждаются после установки на сервере.


## Обновление только мониторинга из GitHub

У администратора мониторинга вверху отдельной страницы приложения есть **«Обновить из GitHub»** и **«Статус обновления»**. Страница управления — `/split-monitoring/updates/`. Аналитики и режим просмотра от другого пользователя обновлять код не могут. POST защищён Django CSRF. Кнопка «Обновить из базы» остаётся отдельной операцией чтения SQL.

Обновление получает только `bse-sb/Split-monitoring`, ветку `main`, в новый локальный каталог. Репозиторий портала, его окружение, миграции, планы и расчёты не меняются. Исходники мониторинга и его зависимости размещаются отдельно в `.local/split-monitoring/releases/` и `venvs/`. Рабочие файлы из `data/` репозитория не копируются поверх локальных снимков.

Этапы: получение коммита → проверка релиза и сборки → отдельное Python-окружение → запуск и расчёт карточки на копии данных → переключение backend мониторинга. До переключения работает прежняя версия; при неудачном запуске восстанавливаются предыдущая конфигурация и backend. Показаны общее время и время каждого этапа. Повторное нажатие во время работы открывает текущий запуск.

На сервере нужен установленный **Git** и настроенный доступ к приватному репозиторию для **той учётной записи, которая запускает портал**. Подключение GitHub к ChatGPT не выдаёт доступ Windows-серверу. Проверьте от служебной учётной записи:

```powershell
cd "C:\Users\ETLadmin\Desktop\Python\PortalComp\pythonProject1\model_purch"
git ls-remote https://github.com/bse-sb/Split-monitoring.git refs/heads/main
```

Настройте Git Credential Manager под этой учётной записью. Обновляющий процесс не открывает интерактивный вход; токены в форму портала не вводятся. Подробные локальные журналы каждого запуска: `.local/split-monitoring/updates/<id>/worker.log` и `commands.log`. Конфигурация, управляющий токен и вывод Git через веб не выдаются.

**Контракт сборки:** если исходники интерфейса не изменились, используется прежняя проверенная `app/dist`. Если изменились — целевая версия репозитория должна содержать соответствующую готовую сборку `app/dist/index.html` и `data-app-build.json` формата `separate-data-v1`, подготовленную штатной сборкой приложения. Проверяются SHA256 HTML и снимка. Снимок можно не хранить в Git, если его точная версия с тем же SHA256 уже есть локально. Если сборки или нужного снимка нет, обновление останавливается **до остановки рабочей версии**. Обычная сборка Vite с другим форматом не подменяет штатную сборку.

Однократно обновите сам портал, чтобы получить эту кнопку. Следующие нажатия обновляют только мониторинг. Первичная установка полного ZIP остаётся обязательной: рабочие данные и первоначальная проверенная сборка не загружаются из пустого репозитория исходников.


## Установка полного приватного ZIP через браузер

Администратор портала или администратор проекта «Мониторинг сплитов» открывает **«Установить ZIP / статус обновления»** в верхней панели приложения либо `/split-monitoring/updates/`. В разделе **«Установить полный ZIP-пакет»** выбирает полученный по внутреннему каналу `rac-line-card-portal-private.zip` и нажимает **«Проверить и установить ZIP»**. Если автор передал SHA256SUMS.txt, значение SHA-256 для этого ZIP можно вставить в отдельное поле. Загружать архив в GitHub и настраивать серверные Git credentials для этого способа не нужно.

Лимит архива — **64 МБ**, распакованного содержимого — **200 МБ**. На HAProxy/IIS при наличии собственного ограничения загрузок оно должно разрешать такой запрос. Форма защищена CSRF и ролями; аналитики и режим просмотра от другого пользователя загрузку/установку выполнить не могут. Архив и журналы сохраняются только в закрытом `.local/split-monitoring/updates/<id>/`, вне статической раздачи.

Портал вычисляет SHA-256 ZIP, проверяет указанный внешним отправителем хеш (если введён), PACKAGE_MANIFEST.json, состав и SHA-256 всех файлов и раздельной сборки app/dist. Не допускаются выход из каталога, символические ссылки, специальные файлы и повторяющиеся имена. Это проверка целостности, а не цифровая подпись автора: администратор выбирает только доверенный пакет.

Из полного пакета устанавливаются интерфейс и серверные модули, включая snapshot_store.py, в **новый релиз**. Рабочая `data/` из архива не копируется и более свежие серверные снимки не откатываются. Зависимости готовятся в отдельном окружении мониторинга; приложение запускается и рассчитывает проверочную карточку на копии действующих данных. Затем переключается только backend мониторинга, с сохранением origin, порта и управляющего токена. При неудачном запуске восстанавливается предыдущий релиз. Прежние исходники и конфигурация остаются для восстановления. Неизменность коммерческих исходных JSON проверена тестом установки полного переданного пакета.

На странице показаны этапы, их время, общий статус и SHA-256 ZIP. Он не выдаётся за SHA коммита GitHub. Права пользователей, маршруты, аутентификация Django, SQL-схемы и Planning(SB) этой операцией не изменяются. Отдельная серверная учётная запись и её доступ к SQL остаются прежними. Новая версия должна поддерживать имеющийся серверный Python и формат действующих данных; иначе предварительная проверка остановит установку с сохранением рабочего релиза.

Один раз требуется обновить и перезапустить сам портал, чтобы появилась форма. После этого администратор устанавливает следующие полные пакеты без PowerShell. Пакет от 18.11.2026 проверяется при его фактической загрузке; наличие нового интерфейса на корпоративном сервере подтверждается после успешной установки и открытия панели сотрудником.


### Кнопки и «Посмотреть как сотрудник»

Права проекта «Мониторинг сплитов → Администратор» дают обновление без общей роли администратора портала. При обычном входе этого пользователя верхняя панель содержит «Обновить из GitHub» и «Установить ZIP / статус обновления», в том числе по ссылке с `?view=1&tab=dashboard`. Страница управления: `/split-monitoring/updates/`.

«Посмотреть как сотрудник» — отдельный режим без изменений данных: даже при роли администратора целевого пользователя кнопки обновления в нём недоступны. В самостоятельном интерфейсе мониторинга теперь показывается явная жёлтая строка «Просмотр как …» с причиной и ссылкой возврата в портал. Для реальной установки администратор должен войти под своей учётной записью, а общий администратор может выйти из режима просмотра в портале. Этот режим не снимает серверный запрет на POST.
