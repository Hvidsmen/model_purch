# Private coefficient-iteration calculations

Open an existing confirmed upload and click “Выбрать планы и запустить расчёт”. Choose any subset of: Moscow + TT Q4 2026 at 100%; all branches 2027 at 100%; actual 2025 with new coefficients. Select saved plans for the requested years. The importer source (planning/ERP) does not matter: calculations consume the saved portal rows, never a fresh PlanSales read. Full 2027 uses a common policy plan, without inventing employee allocation for hypothetical future sales. Select quarterly/yearly shares (default 80/20) and threshold (default 0.8). The approved formula version supplies only director formulas and period corrections for actual 2025, not uploaded K rates.

Rules: physical Moscow/TT inputs are combined for 2026/2027; branch policy/sales rates come from Moscow. 2026 includes only Q4 and the annual contribution of Q4; 2027 includes all four quarters and their annual contributions. At fact=plan, positive invoice/segment potential is split by the requested shares. Annual accrual, annual payment, quarterly payments, possible payments and total payout are distinct. HEAT is excluded only for policies. Each mapped director is paid separately on their assigned branch/merged base; an identical duplicate director mapping is counted once, conflicting rates after merging are rejected. In 2025 Moscow and TT stay separate, TT uses Moscow branch rates, Volkov's block pays Kuditskaya in TT and Galayda's block pays Chevokin in Moscow, using confirmed employee_2025 selections. Other historical recipients follow their explicit mappings.

Synthetic plan calculations do not connect to DWH. Actual 2025 adapts the existing native template and its tested helpers (historical formulas, author shares exact→goods→planning→branch, positive-author fallback for zero totals, thresholds, Q1 rule, annual catchups). Coefficients and both fallback levels are restricted to the same uploaded branch. XML coefficient precision is decimal(20,18), with the same 18-place rate normalization used by the plan simulator. Blank fact planning groups use 9. OTHER, matching the saved importer, and non-RAC saved goods use the native empty dimension, preventing an empty/* mismatch between plan and fact. Two plan source subqueries are replaced by a caller-local #iteration_plan populated from the saved plan. The procedure header becomes a parameterized batch; all four native output tables become session-local temporary tables. Historical published policy defaults are read under the shared calculation lock and copied into a private #iteration_defaults; the actual matched historical formula grid and prepared RunId are stored with the results. No stored procedure, shared output table, coefficient table, director roster, export log or job is modified. All DWH writes target #temp tables and the connection is closed in finally. Standard prepared-sales readiness, schema and compatibility guards remain active. The global shared lock prevents concurrent export/preparation/main calculation from replacing source configuration during the read; each private batch uses a session-specific transaction lock.

Actual directors reuse the existing director_result rules and the same run's unreplicated sales fact. Sales/director classification key grids must match before reusing that fact; mismatches stop before heavy execution rather than silently losing product dimensions. Director coverage, historical identities and formulas are checked before the native query. Missing branch/type rates, unknown discount segments, mixed-year plans, invalid segment totals, missing original Moscow/TT Q4 plans, duplicate DWH subdivision names or unavailable prepared sales are explicit errors. Missing branch mappings are never borrowed from an unrelated branch or treated as zero.

Migration 0041 adds CoefficientIterationRun. Each run freezes upload/mappings/revision, selected configuration, director formula/correction inputs, and exact dated plan rows with source/version/timestamp/SHA256. Mapping or plan edits do not rewrite previous results. Each scenario is finalized independently; a failed 2025 scenario does not discard completed synthetic scenarios or older runs. HTML and Excel include per-branch kinds, branch subtotals, all-branch kind totals and a grand total, plus original recipients. Detailed native eligibility explanations reuse the existing performance helper on private outputs. Excel separates possible/paid quarterly amounts, annual contributions by quarter, annual accrual/payment and catchups, hiding detail columns with outlines. Stored rates/mappings accompany the export. Excel is available only when the run has finalized.

Only the owning motivation editor can configure, view or download a run. A signed, single-use progress token prevents repeat submissions; progress stays outside financial transactions. A nonblocking OS file lock covers each iteration across web workers, with a database uniqueness constraint as a second guard. If a worker dies, the OS releases its lock; the next lock holder can mark its abandoned running record failed while preserving completed scenario results. A live worker cannot be replaced by another request. No external worker/queue service is required.

Validation: money/rule/access/snapshot/partial-failure tests in test_coefficient_iteration_calculation, SQL generation guards, and an optional Chromium flow test covering plan selection, disabled submit/progress, results and Excel. Existing 2025 and director suites also run. The development environment has no live SQL Server access: generated T-SQL is checked against the existing template and mocked ODBC results, not compiled/executed on production. Production execution and final monetary reconciliation must be observed after deployment.
