# da-dev.daichi.ru: HAProxy и вход TT

Публичный адрес DA портала — **https://da-dev.daichi.ru**. HAProxy `192.168.221.9` завершает TLS и передаёт HTTP на `192.168.221.178:8000`. Профиль относится только к этому порталу; `etl-dev-portal.daichi.ru` не изменяется.

## Применение на сервере: HTTPS с сохранением всех доменов

После обновления портала до актуального `main` выполните под служебной учётной записью:

```powershell
cd "C:\Users\ETLadmin\Desktop\Python\PortalComp\pythonProject1\model_purch"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\configure_da_dev.ps1 -Restart
```

**По умолчанию меняются только HTTPS, имя сайта, настройки прокси, CSRF/cookies и origin мониторинга.** Текущие параметры доменного входа, включая обнаружение леса и доверенных доменов, сохраняются. Скрипт не подключается к TT, не устанавливает LDAP-зависимости и не меняет пользователей/права. Сбой LDAPS TT не препятствует применению HTTPS. Это не добавляет доступ к доменам, которых не было в прежней рабочей конфигурации.

`-HttpsOnly` и management-флаг `--https-only` сохранены для совместимости и дают то же поведение. Если задача называется иначе, добавьте `-TaskName "Имя задачи"`. Без `-Restart` профиль сохраняется до следующего запуска.

Настройки находятся в игнорируемом Git файле `.local/site-settings.json`; прежний профиль сохраняется в `.json.bak`. Файл имеет приоритет над устаревшими переменными окружения задачи Windows для перечисленных в нём настроек. Параметры базы в `.local/config.json` и строки подключения не заменяются.

## Необязательный отдельный режим: только TT

**Для портала со всеми внутренними доменами этот режим не применяется.** Он оставлен для отдельной установки, которой нужен только TT, и требует явного выбора:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\configure_da_dev.ps1 -ConfigureTtLdaps -Restart
```

Management-эквивалент — `configure_da_dev --configure-tt-ldaps`. Только этот режим устанавливает `ldap3`, проверяет TLS без пароля и после успешной проверки заменяет параметры AD на TT. При ошибке проверки настройки не меняются. При необходимости публичной цепочки CA можно добавить `-CaCertFile "C:\Certificates\thermotrade-ca-chain.pem"`; без явного выбора TT этот параметр отвергается. Проверка сертификата никогда не отключается.

## HTTPS и доверие к прокси

Профиль задаёт:

- `ALLOWED_HOSTS`: `da-dev.daichi.ru`, прежний IP и loopback для локальной проверки готовности.
- `SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')`, `USE_X_FORWARDED_HOST = True`, `USE_X_FORWARDED_PORT = True`.
- Доверенный адрес прокси — **192.168.221.9**. Первое middleware удаляет forwarded-заголовки у остальных транспортных источников до обработки HTTPS, CSRF и аутентификации. `REMOTE_ADDR` не заменяется значением X-Forwarded-For.
- `CSRF_TRUSTED_ORIGINS = ['https://da-dev.daichi.ru']`, защищённые session/CSRF cookies с именами `da_portal_sessionid` / `da_portal_csrftoken`, без общего cookie-domain для соседних приложений.

HAProxy должен **перезаписывать** forwarded-заголовки клиента. Доступ к backend-порту следует ограничить на сети/сервере. Переадресация HTTP→HTTPS остаётся на HAProxy; Django не делает глобальный redirect, чтобы локальная проверка готовности задачи продолжала получать HTTP 200.

После перехода войдите заново по доменному HTTPS-адресу. По старому HTTP-IP защищённые cookies не отправляются: он подходит для проверки готовности, а не для обычной работы. Продолжительность сессии не меняется.

## Вход TT при явном выборе отдельного режима

- LDAPS: `ldaps://dc-2tt.thermotrade.local:636`.
- Поиск: `DC=thermotrade,DC=local`, рекурсивно (`SUBTREE`).
- Принимаются короткий `логин`, `TT\логин` и `логин@thermotrade.local`.
- После успешной проверки используется существующий канонический пользователь `tt\логин` с тем же PK и назначениями прав; регистр имени не создаёт дубликат. Другие домены к TT автоматически не привязываются.
- Уже существующие локальные учётные записи с локальным паролем сохраняют свой способ входа. При совпадении короткого имени используйте явный `TT\логин` для доменной учётной записи. Локальные записи и AD-пользователи не объединяются по совпадению короткого имени.
- Новому AD-пользователю не выдаются роли или права администратора автоматически. Отключённая учётная запись портала не активируется входом в AD. Пароли AD не сохраняются и в журналы не выводятся. При отказе AD нет перехода к локальному паролю для доменной записи.
- Windows LogonUser/обнаружение других доменов для этого профиля не используются. Отдельный существующий IIS REMOTE_USER-вход не является доверием к HTTP-заголовкам пользователя.

Обычное применение HTTPS сохраняет прежний доменный вход; описанные параметры TT действуют только после явного выбора отдельного режима. Из облачной среды корпоративный DNS/LDAPS может быть недоступен; реальная TLS-проверка выполняется скриптом на сервере внутри сети.

## Мониторинг сплитов

При применении профиля к разрешённым origin установленного приложения добавляется `https://da-dev.daichi.ru`. Его backend останавливается под блокировками запуска/обновления и SQL refresh; следующее открытие запустит его с новым origin. Снимки, исходники релиза и остальные origin сохраняются. Если приложение ещё не установлено, при его установке задайте `-PortalOrigin "https://da-dev.daichi.ru"`.

## Проверка

Откройте доменный HTTPS-адрес: вход по короткому TT-логину, сохранение назначенных разделов после входа, отправка формы с CSRF, карточка мониторинга и обновление из базы. Страница входа не должна предупреждать, что доменный пароль вводится по HTTP. Для явно выбранного режима TT отдельная команда диагностики сертификата:

```powershell
.\.venv310\Scripts\python.exe manage.py check_ad_connection --settings=portal.settings_local
```

При `.venv` замените путь. Если нужно отменить профиль, восстановите `.local/site-settings.json.bak` либо уберите `.local/site-settings.json`, затем перезапустите портал: снова применятся переменные окружения и прежние настройки. Добавленный origin мониторинга можно оставить для совместимости.
