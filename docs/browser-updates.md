# Обновление портала из браузера (Windows)

Общий администратор портала открывает **Администрирование → Обновление портала**,
подтверждает временную остановку и нажимает **Обновить портал**.
Администраторы отдельных проектов и остальные роли не имеют доступа к запуску.

## Одноразовое включение на действующем сервере

Сначала установить версию с этой функцией обычной командой, дождаться PORTAL READY,
затем зарегистрировать отдельное задание **под той же Windows-учётной записью**,
под которой работает существующая задача PortalComp:

```powershell
cd "C:\Users\ETLadmin\Desktop\Python\PortalComp\pythonProject1\model_purch"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\portal-task.ps1 restart -Update
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\portal-task.ps1 enable-browser-updates
```

Для другого имени основной задачи передать `-TaskName` в обе команды. Существующая
основная задача не заменяется. Если она запускается без входа в Windows (Password),
регистрация один раз запросит учётные данные той же Windows-записи. Пароль получает
Task Scheduler; портал его не хранит и через браузер не запрашивает. Для Interactive
используется такой же режим: обновления доступны, пока Windows-пользователь вошёл
в систему. Проверяется совпадение пользователя, режима входа и исполняемых файлов.

Ожидаемый результат регистрации: **BROWSER UPDATES READY**. После этого достаточно
браузера. Новые порты и правила брандмауэра не нужны.

## Выполнение и прогресс

Отдельная задача `PortalComp-Updater` не является дочерним процессом PortalComp.
Остановка веб-сервера её не завершает. Запуск проходит в два запроса: сначала
администратор получает идентификатор и временные права на просмотр/повтор этого
запуска, браузер сохраняет их в sessionStorage, затем запускается отдельная задача.
Таким образом остановка Django не лишает вкладку доступа к статусу.

Задание:

1. Проверяет принадлежность обеих задач этой копии портала, ветку main,
   отсутствие локальных изменений и возможность fast-forward.
2. Получает `origin/main`. Если версия уже актуальна, завершает работу без
   остановки, установки компонентов и повторной подготовки.
3. Останавливает только проверенную задачу PortalComp.
4. На том же адресе/порту временно поднимает сервер статуса, не использующий Django
   или SQLite. Даже во время миграций страница доступна; между передачами порта
   браузер автоматически переподключается.
5. Обновляет код fast-forward, устанавливает requirements и выполняет обычный
   `prepare_local.py`. Перед миграциями создаётся и проверяется
   резервная копия SQLite; для обновления без миграций лишняя копия не создаётся.
   Отображаются реальный процент копирования и этап проверки целостности.
6. После миграций и collectstatic сохраняет одноразовый маркер подготовленной
   ревизии и базы, освобождает порт и запускает PortalComp. `start.ps1` пропускает
   повторную подготовку только после проверки и однократного потребления маркера.
7. Сверяет готовность приложения и точную установленную Git-ревизию. Только после
   этого показывает **Портал готов**. Сам по себе статус задачи Running не означает
   успешного обновления.

Индикатор показывает выполненные этапы, не оценку оставшегося времени. Время и
история отображаются по Москве. Закрытие вкладки не останавливает обновление.
Для текущего подробного статуса при остановленном Django нужна исходная вкладка
с сохранёнными правами; после запуска общему администратору доступна история.
Если вкладка закрылась ещё до старта задания, его можно запустить со страницы
обновлений; права на отслеживание восстанавливаются до остановки сервера.

## Ошибки и повтор

Ошибка до остановки оставляет действующий портал работающим. Изменённые локальные
файлы и расходящаяся история Git не перезаписываются. Если ошибка произошла после
остановки, отдельная задача продолжает показывать статус. Инициатор может нажать
**Повторить обновление**: проверяется свежий origin/main и заново выполняются
подготовка и запуск. Запуск привязан к этой копии портала и фиксированным операциям;
передать произвольную команду, путь, ветку или задачу через HTTP нельзя.

После перезапуска Windows или аварийного завершения задания портал распознаёт
устаревший статус без живого исполнителя и позволяет администратору начать новый
запуск. Просмотр статуса сам не запускает обновление и не меняет данные.

Автоматического отката к старому коду после возможного применения миграций нет.
История запуска и безопасные сообщения находятся в `.local/portal-updates/`;
полный технический вывод — в `<id>/worker.log`, вывод основного сервера —
в `.local/portal-task.log`. В браузер сырой вывод команд и секреты не передаются.

Права на просмотр статуса и управление повтором разделены. Они не находятся
в URL и не позволяют выполнять другие операции. Повтор при остановленном Django
требует отдельный токен управления и совпадение Origin; запросы статуса ничего
не изменяют. Обычный запуск защищён общей ролью администратора и CSRF. Дубликаты
блокируются файловыми блокировками и настройкой IgnoreNew у задачи Windows.

Отключение: удалить `.local/browser-updates.json` и, при необходимости, отдельную
задачу PortalComp-Updater через Планировщик, когда обновление не выполняется.
Основная задача PortalComp не удаляется.

Протокол состояния и одноразового маркера должны сохранять совместимость между
версией запускающего задания и следующей установленной версией.
