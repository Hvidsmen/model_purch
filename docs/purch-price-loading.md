# Загрузка PURCH на большом регистре

При наличии справочника видов цен и совместимых типов ключей загрузчик использует CROSS APPLY / TOP (1) WITH TIES: поиск по модели и виду цены, затем чтение последних строк до конца выбранного дня. Ключи сравниваются в исходном типе; HEX нужен только для вывода. Все строки с одинаковой последней датой сохраняются для проверки неоднозначности.

Если справочник видов цен не обнаружен или типы ключей несовместимы, остаётся совместимый запрос с ранжированием отфильтрованной истории PURCH. Этот путь не обещает быстрого поиска по индексу. Реальное время, logical reads и план необходимо проверить на DataWH.

## Применение индекса

На сервере портала с настроенным DWH_SQL_CONN_STR:

    python manage.py optimize_purch_prices
    python manage.py optimize_purch_prices --apply

Первая команда читает метаданные и индексы, затем печатает DDL. Вторая действительно создаёт недостающий индекс. Нужны права просмотра метаданных и ALTER на регистр.

Индекс: (Номенклатура, ВидЦены, Период DESC) INCLUDE (Цена, Валюта, Единица, Характеристика); фактические имена определяются из метаданных. Если уже есть включённый нефильтрованный индекс с этими первыми тремя ключами (первые два в любом порядке), новый не создаётся.

Для 117 млн строк заранее обеспечьте место под индекс и журнал транзакций. Создание использует ONLINE=ON, MAXDOP=2. Ожидание блокировок ограничено SET LOCK_TIMEOUT 60000. Если редакция SQL Server не поддерживает ONLINE, команда завершается ошибкой. При запуске из кнопки портал показывает предупреждение и продолжает чтение цен без создания индекса. Перехода в OFFLINE нет; его нужно выполнять отдельно в окно обслуживания. При нажатии «Загрузить цены PURCH» администратором портал автоматически проверяет и при необходимости создаёт индекс. Для логиста загрузка DDL не выполняет. Служебная блокировка sp_getapplock не позволяет двум сессиям одновременно создавать индекс. Другие индексы не удаляются и не перестраиваются.

Из рабочей среды разработки корпоративный DataWH недоступен: публикация кода не означает, что индекс создан. После первого запуска загрузки администратором или выполнения команды проверьте фактический план (Index Seek по модели/виду/дате), logical reads и время. Не запускайте создание индекса одновременно из нескольких сессий.

## Статус загрузки

Браузер получает реальные этапы: подключение, метаданные, подготовка, выполнение SQL, чтение пакетами по 1000 строк и сохранение снимка. Во время SQL показан неопределённый индикатор и прошедшее время: точный процент выполнения SELECT неизвестен. Число прочитанных строк появляется при чтении.

Снимок заменяется транзакцией после успешного чтения. При ошибке старый снимок остаётся; ревизия защищает от перезаписи параллельных правок. После успеха ссылка «Показать загруженные цены» открывает актуальную таблицу. Несохранённые правки другой формы блокируют загрузку.

Потоковый endpoint использует WSGI StreamingHttpResponse и X-Accel-Buffering: no. Обратный прокси не должен буферизовать ответ. При обрыве соединения обновите страницу и проверьте снимок перед повтором.

## Область загрузки и лимит

В снимок входят только модели с записью PURCH на выбранную дату. Номенклатура без подходящих цен не добавляется пустыми строками. Запись PURCH с пустой/ошибочной ценой остаётся для диагностики.

Защитный предел — 250000 вариантов (MODEL_DDP_MAX_PRICE_VARIANTS, допустимо 1–1000000). SQL читает максимум предел + 1, затем проверяется превышение. При превышении никакая усечённая часть не сохраняется, старый снимок остаётся. Это предел количества последних вариантов, а не строк исторического регистра. Страницы интерфейса по-прежнему содержат 50 строк.

## Классификация моделей

Классификация не наследуется из PGGoods сценария. Источник — запрос номенклатуры с INNER JOIN на родителя:
- модель: Ссылка / Наименование;
- группа планирования: Даичи_ГруппаПланирования;
- план продаж: Даичи_ГруппаПлановПродаж;
- группа товаров: Наименование родителя по РодительСсылка;
- марка: Марка;
- закупка: Производитель;
- объём и вес: ОбъемЧислитель / ВесЧислитель.

Производитель сопоставляется с именем Purch без учёта регистра и крайних пробелов. SupplyType и PurchaseKind сохраняются снимком из этой карточки поставщика. Если поставщик не найден или вид закупки не задан, загрузка показывает предупреждение; вымышленные значения не подставляются.

Миграция model_purch 0034 добавляет вид закупки в карточку поставщика. Однозначные соответствия из существующих PGGoods переносятся автоматически; конфликтующие остаются пустыми. После обновления выполнить миграцию и повторно загрузить PURCH, чтобы существующий снимок получил классификацию номенклатуры. Ручные помодельные изменения сохраняются при повторной загрузке.

## Контейнер и пошлина

Источник контейнера и пошлины — GoodsGroup («Группы и пошлины»), соответствие по эффективной группе товаров модели с нормализацией регистра и крайних пробелов. Коэффициент пошлины справочника переводится в проценты для формы и формулы: 0,1 → 10%.

Приоритет — ручное значение модели, затем значение справочника. Контейнер и пошлина из группы планирования сценария или общих старых параметров не используются. Если группа отсутствует, значения не выдумываются; расчёт импортной закупки показывает причину. Для закупки РФ логистика и пошлина не участвуют в DDP.

За один запрос/расчёт справочник читается один раз. Новый расчёт использует актуальные значения справочника; повторная загрузка PURCH не требуется. Изменение только формата числа при сохранении не превращает значение справочника в ручное переопределение.

## Копирование из другого помодельного расчёта

Блок «Копировать из помодельного расчёта» предоставляет три режима:
- параметры моделей по текущим фильтрам;
- глобальные расходы и курсы для всего расчёта;
- оба набора вместе.

Фильтры относятся к текущему расчёту и охватывают все страницы, а не только 50 видимых строк. Модель сопоставляется по ссылке номенклатуры, ссылке вида цены и валюте. Несовпавшие строки и строки источника с некорректными параметрами пропускаются с указанием количества. Пустые параметры источника не стирают заполненные значения назначения.

Цены PURCH, дата цен, состав строк и исходные данные ERP назначения не переносятся. Копируются редактируемые параметры; результат считается заново. Только табличное копирование пересчитывает совпавшие строки фильтра. Перенос глобальных расходов/курсов пересчитывает весь набор, в том числе строки вне фильтра. Курсы сохраняют указанную в предпросмотре дату источника в метаданных; пользователь проверяет их применимость к дате назначения.

Перед применением показываются область, количества совпадений/пропусков, примеры изменений и глобальные значения. Предпросмотр подписан и привязан к пользователю, источнику, назначению, ревизиям и фильтрам; срок — 30 минут. Изменение данных или параметров справочника, влияющее на перенос, требует нового предпросмотра. Применение и пересчёт выполняются транзакцией; источник не меняется.

## Три шага подготовки DDP

1. «Загрузить цены»: дата и обновление PURCH. После успешной загрузки автоматически открывается проверка цен. Технические подробности загрузки находятся в раскрываемой диагностике; интерфейс показывает реальный этап и время без выдуманного процента.
2. «Проверить цены»: таблица появляется сразу, с классификацией и фильтрами нулевой/отсутствующей цены, неизвестной валюты и типа поставки. «Сохранить параметры моделей» сохраняет текущую страницу без расчёта. «Перейти к расчёту» только меняет шаг.
3. «Рассчитать DDP»: отдельные блоки расходов и курсов, источник расходов и копирование. Единственная основная кнопка сохраняет глобальные значения и правки видимых строк, затем пересчитывает весь набор, независимо от фильтров.

Переходы между шагами свободные; в браузере они сохраняют несохранённые поля. Enter не сохраняет. Если JavaScript отключён, строки нужно сохранить отдельной кнопкой до расчёта.

Миграция 0035 добавляет признак необходимости пересчёта. Правки без расчёта сохраняют старые результаты с отметкой; изменения справочника «Группы и пошлины» также обнаруживаются по отпечатку. Новый расчёт снимает отметку. При частичном копировании состояние строк вне фильтра не скрывается. Excel отмечает устаревшие результаты.

Старые POST-действия расчёта сохранены для совместимости, но дублирующие кнопки из интерфейса удалены. Новое действие workflow_calculate выполняет сохранение и расчёт транзакцией. Неизменённые унаследованные расходы не превращаются в ручные overrides при одновременной смене глобальных настроек.
