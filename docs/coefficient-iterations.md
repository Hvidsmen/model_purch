# Coefficient iteration: first-upload identity review

Open Motivation → Additional reports → New coefficient iteration. An editor uploads the branch policy/sales matrix and the director matrix. Both are parsed and validated before a private `CoefficientIteration` record is created. The original filenames, SHA256 hashes, rate blocks, source row numbers and classifications are retained in JSON; workbook binaries and auxiliary formulas are not stored or evaluated.

Supported input is the grouped K0–K4 format: the classification header may be shifted down, recipient labels occupy cells above each five-column block, branch blocks identify Policies/Sales in the header, and numeric product rows follow the segment labels. Every primary rate must be a finite number between -1 and 1; formulas in primary rates, missing values and duplicate classification keys are rejected. Duplicate labels within one block are deduplicated. Auxiliary cells outside recognized rate blocks do not define recipients or rates. Upload size, expanded ZIP size, sheet dimensions and recipient counts are bounded.

Suggestions use only normalized exact matches (trim/case/ё–е): unique subdivision key first, then a unique subdivision display name; unique active director full name. No substring/fuzzy/initial matching. Duplicate full names and shorthand remain unresolved. An exact director's current subdivision bindings are suggested; manual per-iteration bindings can differ without changing the roster. Merged original subdivisions and explicitly selected archived directors remain available for historical inputs, with archive/merge labels. Archived directors are never automatically selected by ordinary identity matching. The explicit 2025 substitutions below can propose an archived recipient for review.

The review lists the source name, rate block, classification count and directory choices, highlighting incomplete rows. Save draft permits partial mappings. Confirm requires every uploaded recipient to be mapped, revalidates selected IDs and rejects different rate sets assigned to the same kind/person, original subdivision and goods key. Identical repeated rates are harmless. This verifies provided mappings, not plan coverage: absence of branch/type assignments is shown as a warning, never assumed to mean zero. Per-plan coverage and application of year-specific merge rules belong to the subsequent calculation stage.

Only motivation editors can upload/review, and each record is restricted to its owner. POST saves use row locking and an optimistic revision to prevent another tab from overwriting newer choices. Editing a confirmed mapping returns it to draft and clears its confirmation timestamp. Confirmation is not coefficient approval and launches no calculations. No live coefficient, employee binding, warehouse source, schedule or saved calculation is modified.

Deployment includes migration `0038_coefficientiteration`. The mapping stage feeds the private calculation runner described in coefficient-iteration-calculations.md. Migration 0041 adds per-iteration runs; no additional upload is needed for an existing confirmed iteration.

Checks: parser/mapping/access/conflict tests in `test_coefficient_iteration`; optional Chromium first-upload/manual-confirmation flow in `test_coefficient_iteration_browser`. The two supplied iteration-2 workbooks were parsed locally as six branch blocks plus four director blocks, each containing 41 product keys and yielding 67 recipient mappings; the private files are not part of the repository.

These two historical choices are required on confirmation; exact unique full-name matches, including archived employees, are proposed for review. The private calculation runner consumes these year-specific mappings; ordinary portal calculations continue using their own approved inputs.
