# Shared motivation subdivision exclusions

The version-independent portal reference is `MotivationSubdivisionExclusion` (migration 0043). Manage it in Django admin → «Исключения подразделений из мотивации». Rows have SubdivisionName, enabled and comment; the admin checks trimmed case-insensitive duplicates. Initial enabled names: E-Com, Retail, Брендинг, Прочее, СНГ, Д-Маврикий, Буфер, Вентиляция. ДПП is not a subdivision-name exclusion: channel ДПП and PlanningGroupSalesERP HEAT (including numbered variants) are excluded only for policies. Sales and directors use the full participating base.

No version/year/source field exists on the reference. Authenticated requests and public import/calculation/report entry points load a fresh DB snapshot into a ContextVar; nested helpers reuse it. An operation never changes scope halfway through because an administrator edits the reference. Helpers used purely to generate SQL can use the initial defaults outside an operation; production entry points establish the database context. SQL literals are quoted centrally. Empty enabled lists allow all names. SubdivisionKey is only the source join identity; scope filtering and motivation aggregation use SubdivisionName. The active subdivision manager also tests names, never physical keys.

The same predicate is used for planning/ERP imports, fact consumption in native calculation preparation, all motivation types, policy author allocation/eligibility and report readers. The old native exclusion DELETE is structurally recognized and replaced with the shared predicate for every coefficient type. Static SQL snippets carry a scope placeholder resolved before execution, including author-share caching and progress boundary recognition. The original reviewed SQL/template list is retained only as a structural compatibility guard, not an active business list.

Import keeps channel ДПП for participating names. Full O0–O4 amounts remain in segment_amounts; P0–P4 hold the separate policy base (zero for channel ДПП or HEAT). This preserves one full plan and distinct policy amounts even when multiple keys/channels aggregate to the same name. Physical key receipts retain their channel. Global/local plan calculations, compact summaries, comparison/balancing and private full-plan scenarios consume the corresponding policy/full bases. Existing lines without P values remain readable using their previous full base, with HEAT excluded at calculation time; older imports omitted DPP entirely, so reload plans to restore that data. Historical plan/run audit snapshots are not rewritten.

Scope fingerprints include enabled names and invalidate compact summary/configuration fingerprints on the next operation. New private runs retain the exact excluded names and fingerprint in inputs/Excel. After deployment apply migration 0043, reload saved plans and rerun calculations. Existing SQL Agent procedures/views are regenerated when the job is saved or manually started; after changing the directory, save the existing automatic jobs once before their next scheduled run so stored SQL uses the new dictionary snapshot. Previously saved financial results are not recalculated by editing a reference.

Validation covers dictionary edits/empty lists/quoting, operation stability, name-vs-key identity, both plan sources, channel-specific policy bases, native SQL generation, admin permissions and calculation/report regression suites. There is no live SQL Server connection in the development environment: generated T-SQL still requires observation on DWH after deployment.
