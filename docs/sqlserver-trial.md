# Тестовый перенос портала в SQL Server

Назначение: `vm-dwh / Portal_Test`. Это отдельная копия рабочей SQLite,
без переключения production. DataWH остаётся источником корпоративных данных;
его таблицы и индексы этот перенос не изменяет.

## Запуск на Windows-сервере портала

После получения опубликованных изменений выполните PowerShell:

```powershell
cd "C:\Users\ETLadmin\Desktop\Python\PortalComp\pythonProject1\model_purch"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\sqlserver_trial.ps1 -Server vm-dwh -Database Portal_Test -Launch
```

Скрипт создаёт отдельное Python-окружение `.local/sqlserver-trial/.venv` и
устанавливает зависимости, включая django-crispy-forms и mssql-django.
Рабочее окружение, `start.ps1` и `.local/config.json` не меняются.

Нужны SQL Server 2017+, Microsoft ODBC Driver 17 for SQL Server на машине
портала и доступ Windows-пользователя к серверу. Для создания базы нужны права
CREATE DATABASE; альтернативно DBA заранее создаёт **пустую** `Portal_Test` и
даёт этому пользователю db_owner только на ней. Compatibility level должен
быть не ниже 130. Для ODBC 18 задайте до запуска
`$env:PORTAL_TRIAL_DRIVER = 'ODBC Driver 18 for SQL Server'`.

По умолчанию используется Windows authentication. Если нужен SQL-login,
задайте `PORTAL_TRIAL_USER` и `PORTAL_TRIAL_PASSWORD` в окружении процесса;
пароли не передавайте в аргументах и сообщениях. Для внутреннего сертификата
SQL Server, которому Windows не доверяет, предусмотрен явный параметр
`-TrustServerCertificate`; предпочтительно установить доверенную цепочку.

Источник SQLite определяется так же, как в рабочем портале: DJANGO_DB_PATH,
локальная конфигурация, затем db.sqlite3. Путь печатается перед копированием.
При необходимости укажите `-Source 'полный путь к рабочей SQLite'`.

## Что происходит

1. Согласованный SQLite backup API снимает копию, включая зафиксированные WAL-записи.
   Исходный файл открывается только для чтения. Оригинальный снимок сохраняется отдельно.
2. Миграции выполняются на второй копии, затем выгружаются все данные с исходными ID.
3. Создаётся пустая тестовая база с BIN2 collation. Для существующей базы collation
   не меняется. Непустая база или база другого тестового запуска отклоняется.
4. Применяются миграции SQL Server, удаляются только seed-данные нового тестового
   запуска и загружается снимок. Перенос сохраняет пользователей, права, архивы,
   журналы и связи. Веб-сессии не переносятся. Identity-счётчики восстанавливаются.
5. Проверяются количество и SHA-256 значений всех управляемых моделей и M2M-связей,
   JSON, даты, Decimal, ограничения и отсутствие незавершённых миграций.
6. Проба на SQL Server проверяет JSON-фильтры, Unicode, bulk_update, условную
   агрегацию, Decimal и выполнение select_for_update. Её временные записи откатываются.
7. Только после успешной сверки запускается тестовый портал на
   `http://127.0.0.1:8010/`. Остановка — Ctrl+C.

При ошибке запуск прекращается. Существующие базы не удаляются и повторно не
очищаются. Для нового переноса после неудачи используйте согласованную с DBA
пустую базу `Portal_Test_2` (или другой суффикс), указав `-Database Portal_Test_2`.
Скрипт не выполняет DROP DATABASE.

Папка запуска `.local/sqlserver-trial/<время>-<код>` содержит исходный снимок,
подготовленную копию, data.json, run.json, verified.json и probe.json.
**Снимки и data.json содержат рабочие данные и хеши паролей.** Храните их с
ограниченным доступом; не публикуйте и не прикладывайте к обращениям. Отчёты
сверки содержат только имена моделей, количества и хеши. Содержимое media-файлов
не копируется; пути в записях сохраняются.

## Повторный запуск подготовленного контура

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\sqlserver_trial.ps1 -Mode Run
```

Используется последний успешно проверенный запуск; данные повторно не импортируются.
Пользователи входят с локальными паролями перенесённых учётных записей.
AD/SSO в тесте отключены. Cookies, кэш и файловые каталоги отделены от production.
На странице показывается плашка тестового контура. Запрещены внешние SQL-подключения,
SQL-экспорт, проксирование отдельного приложения мониторинга, отправка почты и
обновление рабочего портала. Поэтому загрузка новых PURCH из DataWH в этом контуре
недоступна: проверяются перенесённые снимки и расчёты по ним.

## Что ещё проверить перед решением о переходе

Автоматическая проба не заменяет проверку реальной работы: создание и копирование
сценариев, фильтры, расчёты DDP, Excel, роли и одновременное редактирование двумя
пользователями. В частности, select_for_update проверяется на выполнение SQL,
а конкурентные блокировки и скорость — отдельно на реальном сервере.

Локально в Linux проверены создание/миграции/выгрузка копии SQLite, конфигурация,
изоляция и тесты. Реальный перенос в vm-dwh и совместимость SQL-запросов должны
быть проверены Windows-запуском выше: в среде разработки нет корпоративного
подключения и установленного нативного Microsoft ODBC-драйвера.
