# Вход в AD без LDAP, LDAPS и IIS

Этот режим предназначен для Windows-сервера, уже включённого в домен, например сервера портала в DAICHI. Он вызывает штатный `LogonUserW` с `LOGON32_LOGON_NETWORK` и `LOGON32_PROVIDER_DEFAULT`: Windows проверяет логин и пароль через свою подсистему доменной аутентификации. Нет LDAP-bind, обращения к порту 636 или требования сертификата контроллера домена. Windows сама выбирает доступный DC; имя vm-dc-shuka не нужно задавать в приложении.

Модуль использует стандартный ctypes: дополнительных Python-пакетов для проверки пароля не требуется, права администратора процесса обычно не нужны. Политика домена/сервера должна разрешать пользователю сетевой вход. Портал не выполняет ImpersonateLoggedOnUser и не меняет identity процесса: MS SQL по Trusted_Connection продолжает использовать учётную запись процесса портала.

## Проверить вход до включения в портале

В обычном PowerShell из корня проекта:

```powershell
$env:PORTAL_AD_NETBIOS_DOMAIN = 'DAICHI'
$env:PORTAL_AD_UPN_SUFFIX = 'daichi.local'
# Если ранее включали режим LDAPS, пока отключите его:
$env:PORTAL_AD_AUTH = 'false'
.\.venv310\Scripts\python.exe manage.py check_windows_ad --username 'DAICHI\etladmin' --settings=portal.settings_local
```

Команда запрашивает пароль скрыто **на вашем сервере**, ничего не записывает в БД и не меняет роли. Не присылайте пароль в чат и не указывайте его параметром командной строки. Проверяйте собственную запись; многократные неудачные попытки подчиняются доменной политике блокировок.

## Включить вход через форму

После успешной проверки:

```powershell
$env:PORTAL_AD_AUTH = 'true'
$env:PORTAL_AD_AUTH_METHOD = 'windows'
$env:PORTAL_AD_NETBIOS_DOMAIN = 'DAICHI'
$env:PORTAL_AD_UPN_SUFFIX = 'daichi.local'
$env:PORTAL_WINDOWS_AUTH = 'false'
```

`PORTAL_WINDOWS_AUTH` — отдельный, старый режим автоматического входа через IIS; здесь он не используется. `PORTAL_AD_LDAPS_URL`, `PORTAL_AD_SEARCH_BASE`, CA-файлы и ldap3 не нужны. Перезапустите процесс портала в этом окружении.

Обычные локальные имена вроде `admin` проверяются прежним способом. Доменные имена `DAICHI\username` и `username@daichi.local` проверяются только Windows. После проверки портал получает имя **из SID выданного Windows-токена**, проверяет настоящий домен и приводит имя к `daichi\samaccountname`. UPN и NetBIOS-логин ведут к одной записи. Локальная одноимённая запись без домена не присоединяется автоматически; при отказе Windows перехода к локальному паролю нет.

Новый доменный пользователь создаётся без роли, без административных прав и без локального пароля. Администратор назначает роль как раньше. Уже назначенные роли и профиль существующей записи сохраняются. Этот режим не читает LDAP-профиль и не синхронизирует группы AD. Отключённая запись портала не входит. Windows проверяет доменную учётную запись при новом входе; существующие сессии Django не проверяют домен на каждом запросе.

## HTTPS портала — отдельное соединение

Сертификаты **контроллера домена** здесь не нужны. Но пароль из браузера всё равно должен поступать на портал по HTTPS. HTTP-адрес старого runserver подходит для локальных учётных записей; доменный вход на нём приложение отклоняет. Не путайте это с LDAPS: проверку Windows можно прямо сейчас выполнить командой `check_windows_ad` без сертификатов вообще.

Для веб-входа используйте доверенный HTTPS-шлюз или прямой HTTPS-запуск без IIS из [инструкции](../ad/README.md#прямой-https-без-iis). Для HTTPS-сервера нужны только Cheroot и WhiteNoise (`pip install "cheroot>=10,<12" "whitenoise>=6.8,<7"`), не LDAP-библиотека. Сертификат сайта должен быть доверенным браузерам. Не требуется настраивать сертификаты на vm-dc-shuka.

Автотесты проверяют последовательность WinAPI с имитацией токена и доступ в Django. Реальный вызов LogonUser возможен только на Windows и проверяется указанной интерактивной командой на рабочем сервере.

## Добавить пользователей вручную и назначить права

Администратор открывает «Пользователи и права» в меню портала (`/admin/auth/user/`), затем Add user / «Добавить пользователя».

- Для доменного пользователя укажите **DOMAIN\samaccountname**, например `DAICHI\etladmin`. Используйте фактический логин из whoami, а не произвольный UPN-псевдоним. Имя нормализуется в нижний регистр; дубликаты с другим регистром отклоняются.
- Поля пароля оставьте пустыми: доменную проверку выполняет Windows. Локальный пароль для новой доменной записи не создаётся, пароль AD не меняется.
- Выберите «Роль в портале»: Администратор, Генеральный директор или Логист. «Без доступа» оставляет проекты недоступными. Действующие границы ролей сохраняются: логист — закупки, генеральный директор — мотивация, администратор — все разделы.
- В существующей записи можно изменить имя/почту, роль и признак Active / «Активен». Деактивация запрещает вход. Доменные записи не получают автоматически административные права.
- Для обычного локального пользователя укажите логин без домена и задайте локальный пароль.

Это создаёт запись **в портале**, а не новую учётную запись в Active Directory. Сотрудник должен уже существовать в домене. При входе заранее назначенные роль и профиль сохраняются. Для проверки интерфейса выбранной роли используйте «Просмотреть как пользователь».
