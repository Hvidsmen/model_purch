# Вход под учётной записью Windows через IIS

Режим включается отдельно; обычный запуск через start.ps1 сохраняется. Приложение доверяет только серверной переменной `REMOTE_USER`, которую IIS передаёт через FastCGI после Windows Authentication. HTTP-заголовки с именем пользователя не используются. Нельзя выставлять этот режим на сервере, где клиент может подменить WSGI-переменную REMOTE_USER.

## Проверка Windows-сервера

В PowerShell:

```powershell
Get-Service W3SVC -ErrorAction SilentlyContinue
Get-CimInstance Win32_ComputerSystem | Select-Object PartOfDomain, Domain
whoami
```

`W3SVC` — служба IIS. Если вывода нет, IIS, вероятно, не установлен. В Windows Server выполните из PowerShell администратора:

```powershell
Get-WindowsFeature Web-Server, Web-Windows-Auth, Web-CGI
```

Для Windows 10/11 вместо этого:

```powershell
Get-WindowsOptionalFeature -Online -FeatureName IIS-WebServerRole
Get-WindowsOptionalFeature -Online -FeatureName IIS-WindowsAuthentication
Get-WindowsOptionalFeature -Online -FeatureName IIS-CGI
```

Нужны Windows Authentication и CGI/FastCGI. Установка компонентов и привязка сайта выполняются на Windows-сервере администратором. Для выбранного intranet-варианта сервер и рабочие станции должны иметь доступ к домену; для обычного автоматического Windows-входа используется доменное окружение.

## Развёртывание

1. Используйте существующий Python 3.10 и `.venv310`. Мост wfastcgi устаревший; совместимость с реальным IIS должна быть проверена при развёртывании. Этот вариант не предназначен для Python 3.12+. Если политика организации запрещает FastCGI/wfastcgi, потребуется другой способ интеграции; включать доверие к заголовкам самостоятельно нельзя.
2. Из корня репозитория установите зависимости:

   ```powershell
   .\.venv310\Scripts\python.exe -m pip install -r requirements-iis.txt
   .\.venv310\Scripts\python.exe manage.py migrate --settings=portal.settings_local
   .\.venv310\Scripts\python.exe manage.py collectstatic --noinput --settings=portal.settings_local
   ```

3. Сохраните резервную копию рабочей SQLite. Создайте отдельный пул приложений IIS (No Managed Code, 64-bit), сайт и HTTPS-привязку по DNS-имени портала. Назначьте пулу чтение кода/venv и запись в каталог SQLite (SQLite создаёт служебные файлы рядом с БД), media и отдельный каталог журналов. Не выдавайте запись во весь код.
4. Зарегистрируйте точную пару python.exe + wfastcgi.py в FastCGI Settings IIS (либо установите мост командой `.\.venv310\Scripts\wfastcgi-enable.exe` из PowerShell администратора). Путь должен совпадать с `scriptProcessor` обработчика.
5. Возьмите `web.config.example` как шаблон, замените пути, DNS-имя и YOURDOMAIN на фактическое **NetBIOS-имя домена**, например CONTOSO. Несколько разрешённых доменов задаются через запятую. Разместите результат как web.config в корне сайта. Не публикуйте рабочую конфигурацию с секретами.
6. В окружении FastCGI worker настройте постоянный `DJANGO_SECRET_KEY` и используемые `DWH_SQL_CONN_STR`/`MS_SQL_CONN_STR`. Перезапустите пул после изменения окружения. Для HTTPS задайте `DJANGO_SECURE_COOKIES=true`. Не включайте DEBUG на рабочем сайте.
7. Для сайта оставьте **Anonymous Authentication** включённой, а **Windows Authentication** выключенной. Только для пути `/accounts/windows/` включите **Windows Authentication** и отключите **Anonymous Authentication** (это задано в шаблоне через location). Остальные страницы защищает авторизация Django. Если секции конфигурации заблокированы, задайте их на уровне IIS, а не ослабляйте настройки приложения.
8. Создайте отдельные виртуальные каталоги `/static` и `/media` на соответствующие каталоги, с обработкой IIS StaticFile вместо наследуемого Python-обработчика. Для static сохраните read-only доступ. Не разрешайте исполнение загруженных media-файлов. Не направляйте сайт в SQLite/каталоги конфигурации как в статические каталоги.
9. Откройте сайт с доменной рабочей станции по DNS-имени. Для Edge/Chrome может потребоваться корпоративная политика intranet/allowlist автоматической аутентификации; для Kerberos со служебной учётной записью и собственным именем сайта SPN настраивает администратор домена. На странице входа доступна кнопка «Войти через Windows», ведущая на защищённый IIS путь `/accounts/windows/`. Обычная форма логина и пароля Django сохраняется для локальных пользователей. Не вводите доменный пароль в форму Django: Windows Authentication выполняет IIS.

Не запускайте параллельно открытый для сети runserver на порту 8000 как обход IIS. Для возврата к прежнему режиму остановите сайт IIS и запускайте start.ps1 без PORTAL_WINDOWS_AUTH.

## Права пользователей

При первом успешном Windows-входе создаётся локальная запись `domain\username`, в нижнем регистре, без пароля и без роли. Она не связывается автоматически с локальным `admin` или `username` без домена. Роли и дополнительные права автоматически не выдаются и из групп AD пока не синхронизируются.

Администратор назначает роль существующим экраном `/admin/auth/user/`. Для начального назначения доменной административной роли можно войти обычным локальным администратором. Либо заранее создайте локальную запись для своего доменного логина и назначьте роль «Администратор» (не нужно задавать ей доменный пароль). Это сохранит административный доступ после перехода. Обычные локальные пользователи и локальный администратор по-прежнему входят через форму Django; её права проверяются приложением.

Заблокированный в портале пользователь не входит. Удаление/блокировка доменной учётной записи проверяется IIS при Windows-аутентификации; уже выданные Windows-билеты зависят от доменной политики. Выход из Django завершает сессию портала, но браузер может снова войти под текущей учётной записью Windows: это нормальная работа SSO.

## Проверка после включения

- Доменный пользователь появляется с полным `domain\username`; без роли проектные разделы недоступны.
- После назначения роли доступны только разрешённые разделы.
- HTTP-заголовки `Remote-User` и `X-Remote-User` не меняют пользователя.
- Недопустимый домен и неактивная запись портала не дают доступ.
- Статика, выгрузки Excel и подключение DWH работают под identity пула (оно не обязано совпадать с пользователем браузера). Trusted_Connection к MS SQL использует identity процесса; делегирование учётных данных пользователя не реализовано.

Автотесты проверяют обработку доверенного REMOTE_USER и права в Django; в Linux-среде не проверяются NTLM/Kerberos, настройки IIS, сертификаты и политики браузеров.

## Просмотр как пользователь

В меню администратора есть «Просмотреть как пользователь». Выберите активную запись: меню и доступ к разделам будут соответствовать её правам. Сессия остаётся административной, данные и роли выбранного пользователя не изменяются. Запросы на изменение данных и запуск расчётов блокируются. Баннер показывает режим и кнопку возврата; все вкладки одной сессии используют выбранный режим. Это проверка интерфейса и прав портала, а не вход в Windows от имени выбранного сотрудника.
